# 00 — DeepSeek 协作规范

> 本文件是所有任务文件的**通用基础**。每个任务的 Prompt 都假设你已遵守本规范。
>
> 目的：把"人记得的项目规范"固化成"每次喂给 DeepSeek 的显式约束"，对抗 DeepSeek 的漂移与过度设计。

## 一、通用 Prompt 模板

**每个任务文件的「💬 喂给 DeepSeek 的 Prompt」都遵循以下结构。** 你可以直接复制任务文件里的 Prompt，也可以根据实际情况微调，但**不要删掉「硬约束」和「禁止项」两段**——它们是防漂移的核心。

````markdown
# 任务：[任务标题]

## 角色与上下文

你是一名资深前端工程师，正在协助维护一个已上线的 React 19 + TypeScript + Supabase 的学生会内部平台。
项目由单人维护，用户量 50-200 人，移动端 PWA 优先。技术栈：React 19 / TS 6 / Vite 8 / Ant Design 6 / Supabase。

## 任务目标

[具体目标，一句话说清]

## 硬约束（违反即返工）

1. **只改任务指定的文件**，不碰其他文件。如需改其他文件，先在回复里说明理由并等我确认。
2. **不新增模块目录**，不修改路由配置，不修改已有 UI 主题风格。
3. **代码规范**：
   - 使用 `import { logger } from '../../diagnostics'` + `const log = logger.for('模块/组件名')`
   - Service 层 catch 后 `log.error()` + 返回安全默认值（`[]` / `null` / `false`）
   - 独立查询用 `Promise.all` 并行，禁止串行 `await`
   - 列表查询必须 `LIMIT`
   - 禁止在 `.map()` / `for` 内调用 `supabase.from()`（N+1 反模式）
   - 非关键操作用 fire-and-forget：`.catch(() => {})`
   - 跨模块类型引用用 `import type`
4. **不写 TODO / TBD / 占位符**，所有代码必须可运行。
5. **不引入新依赖**，除非任务明确要求。
6. **Supabase 查询**：用 `.select('*, join:foreign_key(fields)')` 联表，`.maybeSingle()` 查可能不存在的行。
   postgrest-js 返回的是 `PromiseLike` 不是标准 Promise，**不要用 `.catch()`**，用 `async/await + try-catch` 或解构 `{ data, error }`。

## 禁止项

- ❌ 顺手重构无关代码（即使你觉得"可以更好"）
- ❌ 改变量命名风格（项目用 camelCase 函数 + 下划线 DB 字段）
- ❌ 加注释解释"为什么这么改"（除非逻辑非显然）
- ❌ 修改 CSS 主题色 / 间距体系
- ❌ 把单个文件拆成多个文件（除非任务明确要求）

## 输入：当前代码

【上下文代码】← 把任务文件里列出的上下文文件内容粘贴到这里

## 输出要求

请按以下格式输出，不要输出其他内容：

### 1. 修改的文件清单
- `路径` — 改动说明（一句话）

### 2. 完整代码
对每个修改的文件，输出**完整的新文件内容**（不要用 diff 片段，要能直接覆盖）。

### 3. 数据库迁移（如有）
```sql
-- 迁移 SQL，附在 supabase-migration.sql 末尾
```

### 4. 自检清单（你已完成的自检）
- [ ] 只改了指定文件
- [ ] 无 N+1 查询
- [ ] 无串行 await（独立查询已 Promise.all）
- [ ] 错误处理返回安全默认值
- [ ] 无 TODO / 占位符
````

## 二、DeepSeek 避坑指南

### 坑 1：漂移（多轮后忘记约束）

**现象：** 第一轮严格遵守规范，第三轮开始用 `.catch()`、引入新依赖、改无关文件。

**对策：**
- **一个任务一个会话**，做完就开新会话。
- 如果必须多轮（比如改完 build 报错要修），每轮回复开头**重发「硬约束」段落**。
- 会话超过 5 轮 → 强制开新会话，把当前代码状态作为新会话的「输入」。

### 坑 2：过度设计

**现象：** 你让它加个密码强度校验，它顺手给你加了"密码强度可视化进度条 + 常见密码字典 + zxcvbn 库"。

**对策：**
- Prompt 里写明**最小实现**（"用正则校验即可，不要引入库"）。
- 看到回复里有计划外的功能 → 直接说"删掉 X，只保留 Y"。
- 「禁止项」段落是最后一道防线。

### 坑 3：编造 API

**现象：** DeepSeek 可能编造 Supabase 或 antd 不存在的 API（如 `supabase.from('x').upsertMany()`）。

**对策：**
- 上下文代码里**给出同文件已有的真实用法**让它模仿。
- 验证步骤里**必须跑 build**，TS 会拦住大部分编造的 API。
- 对 Supabase 特定 API 不确定时，让它"参考我给的上下文代码里已有的写法"。

### 坑 4：返回 diff 而非完整文件

**现象：** 你让它改文件，它返回 `<<<<<<< HEAD` 风格的 diff，难以直接应用。

**对策：**
- Prompt 模板里已明确要求"输出完整新文件内容"。
- 如果它还是返回 diff → 回复"请输出完整的文件内容，不要用 diff 格式"。

### 坑 5：忽略 TypeScript 类型

**现象：** 用 `any`、不导出接口、类型定义缺失。

**对策：**
- 硬约束第 3 条已要求类型规范。
- build 时 `tsc -b` 会拦住，把报错粘回去让它修。

### 坑 6：数据库迁移不写注释

**现象：** 给一段 SQL，不说明是追加到 migration 文件还是要单独执行。

**对策：**
- 任务文件里明确标注「数据库变更流程」：
  1. 先在 `supabase-migration.sql` 末尾追加 DDL
  2. 代码中先写好对应 Service 函数
  3. 提醒用户手动执行迁移
- DeepSeek 输出的 SQL 要带注释说明用途。

## 三、通用约束（从 CLAUDE.md 摘录，每个任务都会引用）

这些是项目级铁律，**所有任务都必须遵守**：

### 代码规范
- 诊断日志：`import { logger } from '../../diagnostics'` + `const log = logger.for('模块/组件名')`
- 类型定义放 Service 文件，组件 `import type` 引用
- Supabase 联表：`.select('*, join:foreign_key(fields)')`
- 错误处理：Service 层 catch → `log.error()` → 返回安全默认值
- 类型导入：跨模块用 `import type`

### 性能铁律
- 独立查询必须 `Promise.all` 并行
- 列表查询必须 `LIMIT`（通知 20，活动流 5，搜索 5）
- 禁止 `.map()` / `for` 内调 `supabase.from()`（N+1）
- 非关键操作 fire-and-forget：`.catch(() => {})`

### 乐观更新
- 先改本地 state → 后台同步 → 失败回滚
- **必须用 `setState(prev => prev.map(...))` 而非对象 mutation**

### 模块结构
```
module/
├── index.tsx            # 集中导出
├── XxxService.ts        # 数据层
├── XxxComponent.tsx     # 页面/组件
└── xxx.module.css       # CSS Modules
```

### 数据库变更流程
1. 先在 `supabase-migration.sql` 末尾追加 DDL
2. 代码中先写好对应 Service 函数
3. **提醒用户手动执行迁移**（复制 SQL → Supabase Dashboard → SQL Editor）
4. 用户确认执行后，功能才能正常使用

### Realtime 订阅
- 每新增 `.channel().subscribe()` 必须在 `useEffect` cleanup 中取消
- Supabase 免费层上限 200 并发连接
- 新增订阅前确认不超限

## 四、验证流程（每个任务完成后必须执行）

```
┌─────────────────────────────────────────────────────┐
│  1. 应用代码改动到项目文件                            │
│  2. npm run build  → 必须 0 error                    │
│     失败 → 把完整报错粘回 DeepSeek 修                │
│  3. npm run dev → 浏览器手动验证（按任务验收清单）    │
│  4. 数据库迁移任务：Supabase Dashboard 执行 SQL       │
│  5. 全部通过 → git commit（用任务文件给的 message）   │
│  6. 进入下一个任务                                    │
└─────────────────────────────────────────────────────┘
```

**关键原则（引用项目 CLAUDE.md）：**
> No completion claims without fresh verification evidence.
>
> Build 通过 ≠ 功能正确。必须实际运行验证。

## 五、Commit 规范

每个任务文件末尾会给出建议的 commit message，格式：

```
类型(模块): 中文描述

[任务ID] 任务标题
```

示例：
```
fix(tickets): 抢票改用原子 UPDATE 防止超卖

[P0-01] 抢票并发安全
```

执行：
```bash
git add <任务涉及的文件>
git commit -m "..."
# 不要自动 push，等一批任务做完再 push
```

## 六、版本号更新（面向用户的部署才需要）

**注意：** 不是每个任务都要更新版本号。只有"累积了一批改动准备给用户用"时才更新。

更新两处：
1. `public/version.json` — 递增 `version`，更新 `date` 和 `changelog`
2. `public/sw.js` — `CACHE_VERSION` 与 version.json 一致

版本号规则：`主版本.次版本.修订号`（如 `3.2.0` → `3.2.1`）

建议节奏：
- P0 全部做完 → 发一个 `3.3.0`（安全大版本）
- P1 全部做完 → 发一个 `3.4.0`
- P2 按功能发 `3.5.0` / `3.6.0`

## 七、如果 DeepSeek 不配合

| 情况 | 应对话术 |
|------|---------|
| 它要重构无关代码 | "请只修改任务指定的文件，其他文件不要动。这是硬约束。" |
| 它返回 diff | "请输出完整的文件内容，不要用 diff 格式，我要直接覆盖。" |
| 它引入了新依赖 | "不要引入新依赖，用项目已有的库实现。如果确实需要新依赖，先告诉我理由等我确认。" |
| 它编造了 API | "这个 API 不存在。请参考我给的上下文代码里已有的 Supabase/antd 用法。" |
| 它加了太多功能 | "这是过度设计。请删掉 X 和 Y，只保留最小实现。" |
| 它用 `any` | "不要用 any，定义明确的接口类型。" |
