## 二、推荐执行顺序（串行 + 局部并行）

### 阶段一：P0 安全清零（约 3 天）

```
Day 1（上午）:
  ├─ P0-01 抢票并发安全        ← 会话 A
  ├─ P0-02 文件上传安全增强    ← 会话 B（并行）
  └─ P0-05 密码强度与登录限流  ← 会话 C（并行）
  晚上统一 build + commit

Day 1（下午）~ Day 2:
  └─ P0-04 邀请码机制增强      ← 串行（DB 结构变了，影响 P0-03）

Day 2（下午）~ Day 3:
  └─ P0-03 RLS 全表审计        ← 在 P0-04 之后做，审计新结构
```

**阶段一检查点（全部 P0 完成后）：**
- [ ] `npm run build` 0 error
- [ ] 所有 SQL 迁移已在 Supabase Dashboard 执行成功
- [ ] 抢票功能：手动测试并发（开两个浏览器同时抢最后一张票）
- [ ] 文件上传：尝试上传 `.exe` 被拒
- [ ] 登录：连续输错 5 次密码被锁定
- [ ] 邀请码：用过期码注册被拒
- [ ] RLS：用普通用户账号尝试越权查询被拒
- [ ] git commit + tag `v3.3.0-rc1`

### 阶段二：P1 体验优化（约 4.5 天）

```
Day 4:
  ├─ P1-01 helpers 拆分         ← 会话 A（影响面大，单独做）
  └─ P1-03 SW 版本检测优化      ← 会话 B（并行，独立文件）

Day 5:
  ├─ P1-02 埋点聚合迁移         ← 会话 A
  └─ P1-04 Service 层包装器    ← 会话 B（并行）

Day 6:
  └─ P1-05 注册流程事务化       ← 串行（依赖 P0-04 的新表结构）

Day 7:
  └─ P1-06 通知表自动归档       ← 独立
```

**⚠️ P1-01 与 P1-04 的注意事项：**
- P1-01 改 `helpers.ts` 会影响几乎所有文件，**必须单独做**，做完 build 确认无破坏再继续。
- P1-04 改所有 service 文件，**建议在 P1-01 之后做**（避免文件状态混乱）。
- 如果时间紧，P1-04 可以跳过（它主要是减少重复代码，不影响功能）。

**阶段二检查点：**
- [ ] `npm run build` 0 error
- [ ] 首屏加载：打包体积对比（`npx vite-bundle-visualizer` 或看 build 输出）
- [ ] 数据看板：`activeUsers7d` 仍然正确显示
- [ ] PWA：更新版本后能及时收到通知
- [ ] git commit + tag `v3.4.0-rc1`

### 阶段三：P2 按需（约 6-8 天）

```
P2-02 文档（随时，建议先做，为换届交接准备）
P2-01 测试（P1 全部稳定后）
```

## 三、并行任务对照表

以下任务**修改不同文件**，可以同时开多个 DeepSeek 会话并行执行：

| 并行组 | 任务 | 各自修改的文件 | 冲突风险 |
|--------|------|----------------|---------|
| 组 A | P0-01 + P0-02 + P0-05 | ticketService / FileUpload / authService+LoginPage | P0-05 改 authService，与 P0-04 冲突，**不能与 P0-04 并行** |
| 组 B | P1-01 + P1-03 | utils/helpers / hooks+sw | 无 |
| 组 C | P1-02 + P1-04 | analytics+migration / 新建safeQuery+service | P1-04 改所有 service，与 P1-05 冲突 |

**绝对不能并行的组合：**
- P0-04 与 P0-05（都改 `authService.ts`）
- P0-04 与 P0-03（P0-03 审计依赖 P0-04 的新表结构）
- P1-01 与 P1-04（P1-04 改 service，P1-01 改 helpers，但 P1-01 会触发全量 build，状态混乱）
- P1-05 与 P1-04（都改 service 文件）

**保守策略：** 如果不确定能否并行，就串行做。单人维护，慢一点没关系，乱套了才麻烦。

## 四、数据库迁移汇总

以下任务需要执行 SQL 迁移，**建议按顺序执行**（避免外键/依赖冲突）：

| 顺序 | 任务 | 迁移内容 | 备注 |
|------|------|---------|------|
| 1 | P0-04 | invite_codes 加列（max_uses, expires_at, revoked_at 等） | 先做，P0-03 审计要用 |
| 2 | P0-01 | 新建 `grab_ticket` RPC 函数 | 独立 |
| 3 | P0-05 | 新建 `auth_attempts` 表 + `check_login_limit` RPC | 独立 |
| 4 | P0-03 | 补充各表 RLS 策略 | 依赖 1 的新结构 |
| 5 | P1-02 | 新建 `active_users_7d` View | 独立 |
| 6 | P1-05 | 新建 `register_student` RPC | 依赖 P0-04 |
| 7 | P1-06 | 新建 `notifications_archive` 表 + 归档函数 | 独立 |

**执行方式：** 每个任务文件会给出完整 SQL，复制到 Supabase Dashboard → SQL Editor → 运行。同时追加到项目的 `supabase-migration.sql` 末尾（用注释分隔）。

## 五、检查点机制（防积累技术债）

### 每个任务完成后的微观检查

每个任务文件末尾都有「🧪 验证步骤」和「📝 验收标准」，必须逐项打勾。

### 每个阶段完成后的宏观检查

```
□ npm run build → 0 error
□ npm run lint → 0 warning（oxlint）
□ grep 连续 await → 无串行化（Promise.all 铁律）
□ grep ".map(" + "supabase.from" → 无 N+1
□ grep "TODO\|TBD\|FIXME" → 无残留
□ 角色矩阵：用 volunteer / dept_head / president 三视角验证数据过滤
□ Realtime：新增订阅了吗？cleanup 正确吗？总连接数 < 200？
□ git log --oneline → commit message 规范
□ 更新 docs/ISSUES.md（新发现的问题）
```

### 全部完成后的最终检查

```
□ 打包体积对比（与 v3.2 对比，应减小或持平）
□ Lighthouse PWA 评分 ≥ 90
□ 移动端真机测试（iOS Safari + Android Chrome）
□ 备份 supabase-migration.sql 到云端
□ 更新 README.md 的版本号
□ git tag v3.x.0
□ 通知用户（学生会成员）有新版本
```

## 六、跳过策略（时间紧时怎么取舍）

如果时间非常紧（比如下周就要换届交接），按以下优先级**必须做完**：

```
P0-01 抢票并发安全     ← 必做（超卖会引发舆情）
P0-04 邀请码机制增强   ← 必做（防幽灵账号）
P0-05 密码强度         ← 必做（防撞库）
P0-02 文件上传校验     ← 已有基础校验，可暂缓增强
P0-03 RLS 审计         ← 重要但可延后（当前 RLS 应该是有效的，只是没审计）
P1-01 helpers 拆分     ← 必做（778KB 首屏杀手）
P2-02 ADR 文档         ← 必做（换届交接刚需）
```

**可以跳过的：**
- P1-04 Service 包装器（纯重构，不影响功能）
- P1-06 通知归档（数据量还没到瓶颈）
- P2-01 单元测试（理想情况做，没时间跳过）
- P2-03 新功能（看需求）
