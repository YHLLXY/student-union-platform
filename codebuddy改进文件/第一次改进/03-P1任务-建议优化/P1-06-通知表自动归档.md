## 🎯 任务背景

**问题：** `notifications` 表每个事件一条，200 人 × 每天 5 条 = 1000 行/天，一年 36 万行。虽然 PG 扛得住，但 Realtime 订阅 + 查询会变慢。

**当前无归档机制**，数据只增不减。

## ✅ 完成目标

1. 创建 SQL 函数 `archive_old_notifications`，删除 30 天前已读通知。
2. 用 GitHub Action 每天定时调用该函数。
3. 未读通知不删除（避免用户漏看）。

---

## 🚧 硬约束（违反即返工）

1. **只新建 GitHub Action yml + 追加 `supabase-migration.sql`**。
2. **不新建 `notifications_archive` 表**（直接删除，学生会场景历史通知无保留价值）。
3. **只删已读通知**（`is_read = true`）。
4. **只删 30 天前的**（`created_at < now() - INTERVAL '30 days'`）。
5. GitHub Action 用 `supabase` CLI 或 `curl` 调 RPC，**不暴露 service_role key 到前端**。

### 2. SQL 函数

```sql
-- ============================================================
-- 第十九部分：通知归档函数（P1-06）
-- ============================================================

CREATE OR REPLACE FUNCTION archive_old_notifications()
RETURNS INTEGER
LANGUAGE sql
SECURITY DEFINER
SET search_path = public
AS $$
  WITH deleted AS (
    DELETE FROM notifications
    WHERE is_read = true
      AND created_at < now() - INTERVAL '30 days'
    RETURNING 1
  )
  SELECT count(*)::INTEGER FROM deleted;
$$;
```

### 3. GitHub Action

```yaml
# .github/workflows/cleanup-notifications.yml
name: Cleanup Old Notifications

on:
  schedule:
    # 每天北京时间凌晨 3 点执行（UTC 19:00）
    - cron: '0 19 * * *'
  workflow_dispatch: # 支持手动触发

jobs:
  cleanup:
    runs-on: ubuntu-latest
    steps:
      - name: Run cleanup RPC
        run: |
          RESPONSE=$(curl -s -X POST \
            "${{ secrets.SUPABASE_URL }}/rest/v1/rpc/archive_old_notifications" \
            -H "apikey: ${{ secrets.SUPABASE_SERVICE_ROLE_KEY }}" \
            -H "Authorization: Bearer ${{ secrets.SUPABASE_SERVICE_ROLE_KEY }}" \
            -H "Content-Type: application/json")
          echo "Cleanup result: $RESPONSE"
          
          # 检查是否成功（返回数字表示删除的行数）
          if echo "$RESPONSE" | grep -qE '^[0-9]+$'; then
            echo "✅ Deleted $RESPONSE old notifications"
          else
            echo "❌ Cleanup failed: $RESPONSE"
            exit 1
          fi
```

## ⚠️ 风险与回滚

**风险 1：** service_role key 泄漏（GitHub Secrets 被盗）。

**应对：** GitHub Secrets 是加密存储的，只有 Action 运行时才解密。但仍要定期轮换 key。如果泄漏，立即在 Supabase Dashboard 重置 service_role key。

**风险 2：** 误删未读通知（函数写错）。

**应对：** 函数里有 `is_read = true` 条件，未读不会删。测试时先 `SELECT count(*)` 确认范围再执行。

**风险 3：** GitHub Action 执行失败未发现。

**应对：** Action 失败时 GitHub 会发邮件通知（默认设置）。也可以在 Action 里加失败通知步骤。

**回滚：**
```bash
rm .github/workflows/cleanup-notifications.yml
# 函数保留无害（不被调用即可）
```
