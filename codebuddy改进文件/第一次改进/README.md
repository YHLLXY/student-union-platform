# 学生会交流平台 — 改进执行计划（DeepSeek 版）

> 本目录是基于项目审查报告生成的可落地改进计划，专为使用 **DeepSeek（V3/R1）作为开发 Agent** 的工作流设计。
>
> 每个任务文件都是**自包含的**：包含背景、约束、需要阅读的上下文文件、可直接复制的 Prompt、验收清单与验证步骤。

---

## 一、为什么这套计划要为 DeepSeek 定制？

DeepSeek 作为代码 Agent（无论通过 API、Cline、Roo Code、Continue 还是网页对话使用），有以下区别于 Claude Code / Cursor Agent 的特性，本计划的所有设计都围绕这些特性展开：

| DeepSeek 特性 | 对执行计划的影响 |
|--------------|----------------|
| **会话不持久**：每个新会话上下文清零 | 每个任务文件**自包含**，包含完整背景与所需代码片段，不依赖"之前的对话" |
| **无文件系统自动访问**（除非集成 Cline 等） | 任务里**显式列出**需要读哪些文件、文件路径精确到行 |
| **长上下文注意力衰减**（64K+ 但后半段易丢细节） | 单任务范围**严格控制**，避免一次塞 10 个文件；核心约束**重复出现在每个任务** |
| **不主动 build/验证** | 每个任务都有**可执行的验证清单**，用户照着跑即可 |
| **易"过度设计"**（顺手重构无关代码） | 每个任务明确**硬约束与禁止项**，越界即返工 |
| **易"漂移"**（多轮后忘记规范） | 每个任务 Prompt **重申 CLAUDE.md 关键约束** |
| **代码生成质量高**（给定明确规格） | Prompt 给出**输入/输出规格 + 真实代码上下文**，而非模糊描述 |
| **对结构化输入友好** | Prompt 用**分步骤 + 代码块 + Checklist** 组织 |

**核心原则：把"人记得的项目知识"固化成"任务文件里的显式上下文"，让 DeepSeek 每次都从同一基线出发。**

## 三、使用方法（标准工作流）

### 单个任务的标准执行流程

```
1. 打开任务文件（如 02-P0任务-必须修复/P0-01-抢票并发安全.md）
2. 阅读「📂 需要阅读的上下文文件」→ 把这些文件内容准备好
3. 复制「💬 喂给 DeepSeek 的 Prompt」整段
4. 在 Prompt 末尾的【上下文代码】占位处，粘贴第 2 步准备好的文件内容
5. 发送给 DeepSeek
6. DeepSeek 返回修改后的代码 / SQL / 新文件
7. 你把代码应用到项目对应文件
8. 按「🧪 验证步骤」逐项执行验证
9. 全部通过 → git commit（用任务文件里给的 commit message）
10. 进入下一个任务
```

### 批量执行（推荐）

如果你用 Cline / Roo Code 等支持文件访问的 DeepSeek 集成，可以把任务文件 + 上下文文件一起喂给它，让它直接读写。此时：
- 仍然要**一个任务一个会话**，不要在同一个会话里堆多个任务
- 任务完成后**立即验证 + commit**，再开新会话做下一个

## 七、遇到问题怎么办

| 情况 | 处理 |
|------|------|
| DeepSeek 改了无关文件 | 用 `git diff` 检查，只保留任务相关改动，`git checkout` 撤销其他 |
| DeepSeek 越界重构 | 在新会话里重发任务，强调「禁止项」段落 |
| build 失败 | 把完整报错粘回 DeepSeek，让它只修这一处，不要让它"顺便优化" |
| 数据库迁移失败 | Supabase Dashboard → SQL Editor → 看报错；通常是 RLS 阻止或外键约束 |
| 任务做一半想暂停 | commit 当前进度（commit message 加 `[WIP]` 前缀），下次从「验证步骤」继续 |
