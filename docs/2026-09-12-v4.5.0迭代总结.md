## 一、这次真正学到的东西

### 1. 弹窗表单不要在 `afterOpenChange` 里回填——它会吃掉用户刚敲的字

**现象**：资料编辑弹窗点「保存」，提示「资料已更新」，但库里和界面上什么都没变。E2E 抓到的证据干净利落：PATCH 请求体里是**旧名字**。

**根因**：初值用 `Modal` 的 `afterOpenChange` + `form.setFieldsValue()` 回填。这个回调在**打开动画结束（约 300ms）之后**才触发，而 Playwright（以及手快的人）在那之前就已经开始输入了——回填把刚输入的内容覆盖成档案里的旧值。

**教训与规则**：

1. **初值走 `initialValues`，让组件挂载即正确**；不要用「打开之后再赋值」这种有中间态的写法。本项目里现成的写法是条件挂载：`{open && <Form/>}`（`PostList` 的详情弹窗一直是这么写的，照抄即可）。
2. **区分「回填」和「重置」**：需要用户每次打开都看到最新值时，正确做法是**重新挂载**（新 key / 条件渲染），不是往已挂载的表单里塞值。
3. **这类 bug 单测抓不到，E2E 一抓就准**：它依赖真实的时间轴（动画 + 输入交错）。反过来说，凡是「时序相关」的交互，别指望 service 层单测能覆盖。

### 2. stub 保真度有两个层次：报文形态 → 语义缺口

上一轮（v4.4.0）踩的是**报文形态**：stub 对字符串原样输出，而 PostgREST 对标量 RPC 返回带引号的 JSON。这次踩的是更深一层——**语义缺口**：

**现象**：注册流程的新用户**永远不弹新人引导**。而单测里「新用户 onboarded 默认 false」是过的。

**根因**：stub 的 POST 在 `Prefer: return=representation` 时，回传的是「**请求体** + id/created_at」，而不是「**落库后的整行**」。于是 `TABLE_DEFAULTS` 补出来的列（`users.onboarded = false`）在响应里根本不存在 → 前端读到 `undefined` → 严格判断 `=== false` 不成立。真实 PostgREST 返回的是入库行，这个差异只在「断言某个**列默认值**或**触发器派生值**的生效」时才暴露。

**教训与规则**：

1. **stub 的回写响应 = 落库后的整行**。写 stub 时问自己：真实 PostgREST 会返回什么形态？是入库行、还是我的入参回显？
2. **判断 stub 缺口的信号**：如果某个「数据库本该自动产生」的值得不到解释（默认值、触发器维护的计数、序列号），先怀疑 stub 没模拟，别急着改业务代码。
3. 顺手修掉一个连带 bug：多行插入时所有行的 `id` 都取自最后一行——回传入库行之后自然消失。
4. **同一处还有第三种形态**：复合主键冲突（23505）。这次给 stub 补了 `COMPOSITE_PK` 声明并按语句级原子性整条拒绝，前端的「把重复点赞当成功」才真的被测到——否则那条 `error.code !== '23505'` 分支永远是死代码。

### 3. N+1 不只是「循环里查询」，也是「逐行补一个 count」

**现象**：论坛列表原本对每个帖子各发一条 `head: true` 的 count 算回复数。一页 20 帖 = **1 + 20 次往返**。

**为什么值得单独写一条**：它不是经典的「在 `.map()` 里写 `supabase.from()`」，而是被包装成 `Promise.all(data.map(async p => ...))`——**并行所以看起来很快**，但往返次数依然与行数成正比，页面越大越慢，而且它同时挡住了「点赞数」的落点（多一个指标就再多一轮 N+1）。

**解法不是加缓存，而是换载体**：在 `forum_posts` 上放 `reply_count` / `like_count` 两个计数列，由增删对应行的触发器维护，回填语句写进迁移。列表于是退化成**单条查询**，点赞数也顺手有了存放处。

**教训与规则**：

1. **判据换成「每页查询次数是否与行数相关」**，而不是「有没有写在 `.map()` 里」。并行不改变量级。
2. **并行化 ≠ 优化**：`Promise.all` 解决的是延迟，解决不了往返次数。真要减往返，要么改数据载体（计数列/聚合列），要么把计算搬到服务端。
3. 计数列的代价要写在注释里：它是**冗余数据**，唯一真相在触发器，客户端不许写。

### 4. 同一个库里，两种写权限：权益 vs 展示

这轮同时做了两件看似矛盾的事：

- **积分流水**（v4.4.0）：`REVOKE INSERT/UPDATE/DELETE`，只有函数能写，因为积分是**可兑换的权益**，被改就是真损失；
- **帖子计数列**（v4.5.0）：**有意不加守卫**，因为它是**展示数字**，改动它拿不到任何权限、也不影响任何业务判断，刷新就被真实值覆盖。为它加「守卫触发器 + 事务内 GUC 绕行」的复杂度换不来安全收益。

**规则**：给字段定权限时先问「改了它，攻击者得到什么」。得到权益 → 收口到函数 + 守卫触发器；只得到屏幕上难看的一个数字 → 标注清楚即可，别过度设计。**并把这条判断写进注释**，否则下一个人会以为是漏了。

### 5. 按行 RLS 的写法沉淀（Phase 4 C2 的试点）

`forum_likes` / `forum_bookmarks` 是全项目第一批按行 RLS 的业务表，写法固定成四步，Phase 4 往大表推时照这个模板：

1. **复合主键表达「一人一次」**：`PRIMARY KEY (post_id, user_id)` —— 幂等是结构保证的，不是靠前端自律；
2. **逐动作建策略**，不复用 `authenticated_full_access`：SELECT `USING (true)`（计数要给人看）、INSERT `WITH CHECK (user_id = current_app_user_id())`、DELETE `USING (user_id = current_app_user_id())`；
3. **有意不建 UPDATE 策略**，并 `REVOKE UPDATE`——没有可改字段的表，UPDATE 通路本身就是多余攻击面；
4. **客户端把唯一冲突当成功**（`error.code !== '23505'` 返回 true）：策略是服务端的事，双击/重试不该让用户看到报错。

配套经验：`CREATE POLICY` 没有 `IF NOT EXISTS`，可重跑脚本一律 **先 `DROP POLICY IF EXISTS` 再建**。

### 6. 迁移脚本「可重跑」的两个具体坑

1. **存量回填别用 `now()`**：把「老用户标为已引导」写成 `created_at < now()`，重跑一次就会把「上次执行之后新注册的人」也标进去。改成**固定时间字面量**（`< '2026-09-12 00:00:00+08'`），不论重跑多少次口径都一致。
2. **上一轮的教训真的复用上了**：这次 `forum_posts.pinned_at` 的守卫触发器、计数索引都引用新列，所以第 0 节先把六个新列全部 `ADD COLUMN IF NOT EXISTS` 加完——`scripts/check-sql.mjs` 的 DDL 顺序检查**一次就过**，没有再犯 42703。**教训的价值在于把它变成工具里的检查项，而不是写在文档里靠人记。**

### 7. 新功能引入「全屏遮罩」会连锁影响既有 E2E

新人引导抽屉带遮罩（`maskClosable={false}`），一上线就把注册流程用例的「退出登录」点掉了——因为那条用例从来没考虑过「登录后屏幕上还盖着一层东西」。

**教训**：

1. **给已有流程加阻塞式 UI，等于改了所有下游用例的前置条件**。加之前先 grep 一下哪些用例会走到这个界面。
2. 解法不是把遮罩关掉，而是**让用例顺着真实用户的操作走**：新增 `dismissOnboarding(page)`（弹了就点跳过，没弹就空操作），注册用例里显式断言「新用户确实看到了引导」再关掉它。这样既保住了防线，又顺带覆盖了新功能。
3. **反向自证**：该用例最后再调一次 `dismissOnboarding`——如果它是空操作就说明引导真的没再出现，避免「helper 静默失效」把 bug 掩盖过去。

### 8. 安全默认值：前端不能用 `!x` 判断新字段

`onboarded` 是这一轮新增的列。若写成 `if (!user.onboarded) 弹引导`，那么**升级瞬间全体老用户全被弹一次**——因为 v4.4.0 写入的本地缓存里根本没有这个字段，`undefined` 也满足 `!`。

**规则**：判断「新增的布尔字段是否为假」时，用**严格等于**（`user.onboarded === false`），让 `undefined`（旧缓存/未迁移）走「不触发」这一侧。默认行为是「什么都不做」，而不是「全都做一遍」。

### 9. E2E 定位器：`hasText` 匹配的是可见文本，不是 `aria-label`

写提及候选面板的定位器时用了 `page.locator('.ant-popover').filter({ hasText: '选择要提及的成员' })`——那句话是 `aria-label`，`hasText` 看不见它，于是面板明明弹出来了却断言失败。正确写法是 `getByRole('listbox', { name: '选择要提及的成员' })`。

**规则**：定位「有语义角色 + 名字」的元素，一律优先 `getByRole(role, { name })`；`hasText` 只用于筛可见文案。这条和项目已有的 `btn(scope, label)` 封装是同一个思路——**用可访问名定位，比用文本/样式稳**。

## 二、与计划的偏差

| 计划原文 | 实际做法 | 理由 |
|---|---|---|
| 「帖子卡点赞（乐观更新 + 计数）」 | 增加 `reply_count`/`like_count` 计数列 + 两个触发器，列表改单查询 | 计数原本无处安放，顺手把列表的 1+N 一起删掉（见经验 3） |
| 「@提及 → 被提及者收 mention 通知」 | 提及对象由**前端**从点选记录里给，数据库不解析正文 | 通知不是权限；Markdown 千变万化，触发器里解析必然误判，而漏发只是少一条提醒 |

## 五、给下一次接手的注意事项

1. **改动前先看 `CLAUDE.md` 的「Phase 3 数据层」四条**，尤其是「计数列只读」「计数列有意不加守卫」这两条反直觉设计。
2. **动 list/detail 的数据来源时，记得计数列是触发器维护的**——本地乐观更新后不必回查，但也别试图自己写这两个列。
3. **本地跑 E2E 前先确认 stub 的种子账号是 `onboarded: true`**（`dev-stub.mjs` 里有归一化循环在 SEED_SNAPSHOT 之前执行）；新增种子用户若漏了这一步，会被引导遮罩挡住后续点击，报错还很难看出原因。
4. **加新列/新表时，把「存量数据怎么办」写进迁移**（回填 + 可重跑口径），不要留给前端兜底。
