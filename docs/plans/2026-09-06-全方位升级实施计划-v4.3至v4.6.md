## 一、背景与目标

v3.6→v4.2.2 四轮迭代完成了架构现代化（RQ/类型化/分包）、性能（入口 65KB）、UI（暗色/骨架/动效/移动端）与安全基线（RLS 封锁/保活），但**功能面自 v3.1 后未增长**。本计划一次性覆盖用户选定的四个方向，分四个发版节奏推进，每阶段独立可用、可回滚。

**总目标**：把"好看好用但功能停步"的平台推进到"完整作业闭环 + 有质量护栏"。

## 三、分阶段计划

### Phase 0 —— 测试护栏先行（工程质量地基，无用户可见变化）

**为什么最先做**：后续 Phase 1-3 大量触碰 Service 层与数据模型，先有护栏，之后每一步都有回归保障。

1. **基建**：devDeps 加 `vitest` + `@testing-library/react` + `playwright`；测试专用环境变量指向本地 stub（复用 `scripts/dev-stub.mjs`，vitest globalSetup 自动拉起/回收）。
2. **Service 层单测（首批 ~50 case）**：taskService（发布/提交/审核/筛选）、authService（注册/登录/邀请码三函数）、adminService（角色变更/邀请码 CRUD）、notificationService（已读/乐观更新）、helpers（hasMinRole 边界）。
3. **E2E 冒烟 3 条（Playwright + stub）**：① 注册→登录→改密 ② 发布任务→志愿者提交→审核通过 ③ 发布票务→抢票→我的票券。
4. **CI 接入**：deploy.yml 拆 test job（oxlint + vitest + e2e）→ 全绿才允许 deploy job。
5. **验收**：`npm test` 本地与 CI 全绿；故意改坏一个 Service 断言能红。

### Phase 1 —— 数据出口 + 通知升级 + 登录与细节（发版 v4.3.0）

1. **A2 数据导出**：
   - 位置：权限管理-成员管理（成员名单导出）、任务管理（按当前筛选导出）、数据看板（统计汇总导出）。
   - 技术：`xlsx`（SheetJS 社区版，Apache-2.0）**动态 import 懒加载**，不进首屏包；UTF-8 BOM 兜底中文。
   - 验收：导出文件 Excel/WPS 打开中文正常；导出范围与当前筛选一致；无权限角色无入口。
2. **B4 通知升级**：去 20 条硬上限（分页加载）、未读/已读 + 类型 Tab（任务/公告/论坛/系统）、一键全部已读、同类聚合（同 ref 连续通知合并展示）。
3. **B1 登录流优化**：学号输入 debounce 即查 `check_student_registered`——已注册则隐藏邀请码栏并切换按钮文案为"下一步：输入密码"；未注册才要求邀请码。（修掉走查实测的"老用户随便填邀请码"断点）
4. **B5 细节打磨**：全局搜索结果面板排版重排（留白/单行截断/结果分组标题）；任务卡"发布者：未知"线上核实与修复；空态文案统一走 EmptyState。
5. **发版**：version.json/sw.js → 4.3.0，changelog 如实。

### Phase 2 —— 组织者学期闭环：积分 + 票务闭环 + 批量邀请码（发版 v4.4.0）

1. **A3 成员考核积分**：
   - 新表 `points_ledger`（user_id, delta, reason, ref_type, ref_id, semester, created_at）；触发点：任务审核通过 +2、按时提交 +1、逾期 -1、活动签到 +1（与 A1 联动）。
   - UI：个人中心加"我的积分/本学期明细"；权限管理-工作看板加"本学期积分排行"（部门内/全校切换）；导出联动 A2。
2. **A1 票务闭环**：
   - `ticket_records` 加列 `checked_in_at`、`checked_by`；票务详情 **Drawer**（不改路由，遵守模块规范）：剩余/进度条/活动说明/我的票券入口。
   - **QR 双向**：参与者"我的票券"生成签到 QR（内容 = record_id + 短时效签名，`qrcode` 库本地生成，MIT）；组织者端"扫码签到"（`html5-qrcode`，Apache-2.0，调用摄像头）→ POST 签到 → 乐观更新；主办方名单视图（领取/签到统计 + 导出联动）。
   - 防重：同一 record 重复签到幂等返回；时间窗外拒绝并提示。
3. **A4 批量邀请码**：权限管理新增"批量生成"（数量/角色/部门/有效期）→ 生成结果表格 + 一键复制/导出 CSV（打印分发）。
4. **发版**：4.4.0（含**第十八部分**迁移 SQL，用户在 Supabase 执行后功能生效）。

> **数据层已落地（2026-09-11，`supabase-phase2-v4.4.0.sql`）与计划的两处偏差**：
> - 「逾期 -1」→ 改为「**逾期提交 -1**」：逾期是随时间自然发生的状态，靠定时任务扫全表扣分既需要 pg_cron、又会制造「人不在也被扣分」的争议；改为在**审核通过那一刻**用提交时间与 `deadline` 比较来判定，一次判定、可追溯、零定时任务。
> - 二维码「短时效签名」→ 落地为**库内随机密钥 + 15 分钟有效期**的 MAC 令牌：密钥由数据库随机生成、存 `app_secrets` 表（对 anon/authenticated 完全封锁），**不进仓库**；签名用内置 `md5` 做 keyed hash，不引入 `pgcrypto` 依赖。防重与时间边界仍在服务端（`check_in_ticket`），令牌只负责防「截图长期转发」。
> - **附带两处防伪加固**（不加固则积分毫无意义——任何志愿者都能给自己加分）：`task_submissions.status` 进入 `approved`/`rejected` 必须是部门负责人及以上；`ticket_records.checked_in_at`/`checked_by` 只能由组织者写入。两处均放行 `service_role`（未来备份脚本需要）。
> - 积分表 `points_ledger` 是**唯一不套用 `authenticated_full_access` 的业务表**：只给 SELECT，写入口只有 SECURITY DEFINER 函数与触发器（流水账一旦可写就失去意义）。
>
> **首跑报错与修复（2026-09-11，值得记一笔）**：用户执行第十八部分时报 `42703 column "checked_in_at" of relation "ticket_records" does not exist`——**是我把语句顺序写反了**：`CREATE TRIGGER … AFTER UPDATE OF checked_in_at` 排在 `ALTER TABLE … ADD COLUMN checked_in_at` 之前，而 Postgres 在**创建触发器那一刻**就要校验该列存在。修复：把两个新列提到脚本最前面（第 0 节），并在注释里写明「先加列，再挂约束/触发器/索引」这条铁律；`scripts/check-sql.mjs` 新增**关卡 ③ DDL 顺序检查**（触发器的 `UPDATE OF 列`、索引列若引用了本文件后面才 `ADD COLUMN` 的列即报错），并用倒序夹具做了回归自证——它会准确报出「第 3 条语句引用了第 4 条才添加的列」。
> 附带结论：脚本全幂等（5 个 `CREATE TRIGGER/POLICY` 与 5 个 `DROP` 一一配对），失败后**直接重跑同一份即可补齐**，不需要清理半成品状态。

### Phase 3 —— 社区活跃与自助服务（发版 v4.5.0）

1. **A5 论坛互动**：新表 `forum_likes`、`forum_bookmarks`；帖子卡点赞（乐观更新 + 计数）、"我的收藏"筛选、管理员置顶；**@提及**：编辑器输入 @ 弹成员选择 → 渲染高亮 → 被提及者收 `mention` 通知。
2. **B2 新人引导**：首次登录（users 加 `onboarded` 列）弹出三步引导抽屉：①看使用指南 ②认领第一个任务 ③完善个人资料；可跳过，完成后不再出现。
3. **B3 个人资料编辑**：个人中心加"编辑资料"（显示名、头像上传至 Storage 复用 FileUpload、联系方式）——联系方式的部门可见性沿用现有权限规则。
4. **发版**：4.5.0（**第十九部分**迁移 SQL）。

### Phase 4 —— 数据保险 + 权限收口 + 无障碍（发版 v4.6.0）

1. **D1 备份流水线**：每周 GitHub Action（沿用 keepalive 的 secrets 管控）用 service_role 导出全部 17 表 JSON → gzip → 存入**专用私有仓库**（git 历史即版本化备份，保留全量）；附 `scripts/restore-backup.mjs` 恢复脚本；失败走 `::error::` 邮件告警。
2. **D2 外部拨测**：UptimeRobot 免费档监控首页 + version.json（纯配置，文档写清步骤，由用户注册配置）。
3. **C2 细粒度 RLS**（在 E2E 就绪后执行，回归有保障）：
   - 设计原则：辅助 SQL 函数 `is_admin()` / `is_dept_head_of(dept)`；逐表 SELECT/INSERT/UPDATE/DELETE 策略；兼容旧数据 `created_by IS NULL` 场景。
   - 分两批上线（先读后写），每批执行后跑全量 E2E + 三角色矩阵走查。
4. **C3 无障碍**：先出审计报告（表单 label、按钮 aria-label、对比度、焦点顺序），修复高频路径（登录/任务/公告），低频后台列入下轮。
5. **发版**：4.6.0。

## 四、关键设计约束（延续既有铁律）

- **不改路由、不新增模块目录**：详情页用 Drawer/Modal，积分归 profile/admin，签到归 tickets 模块内。
- **动效一律走 `src/components/motion` 封装层**；新交互动效从动效库（E:\homework\开发\特效存储）取材——QR/导出等新组件参照 10-React组件动效 与 01-CSS动画库 样本（AGENTS.md 守则 1）。
- 性能铁律不变：Promise.all 并行、列表 LIMIT、无 N+1、乐观更新不可变式；新依赖一律动态 import 评估进包影响。
- 双外键表嵌套 select 用 `别名:users!列名()` 语法；改表必须同步 `src/types/database.ts`。
- 每阶段收尾：build → lint → 功能验证（浏览器实测对照验收标准）→ 版本链同步 → 提交推送。

**CI 首跑失败与修复（值得记一笔）**：test job 在「Unit tests」步骤 exit code 1 且**没有任何测试输出**——原因是 CI 用 `node-version: 20`，而 vitest 5 的 engines 要求 `^22.12 || ^24 || >=26`、jsdom 30 要求 `^22.22.2 || ^24.15`，Node 20 下 vitest 启动即崩。本地是 Node 24 所以一直全绿。此前部署能用 Node 20 是因为 vite 8 只要 `>=20.19`。修复：两个 job 升到 Node 24，并在 `package.json` 补 `engines.node >=22.22.2`。**教训：CI 运行时版本必须与本地开发对齐；「exit 1 且无输出」通常是加载期崩溃而非断言失败。**

### 偏差与关键发现（均已固化进代码注释与 CLAUDE.md）

1. **stub 保真度是单测可信度的前提**：`.contains()` 线上是 `col=cs.{...}`、计数是 `Prefer: count=exact` + `Content-Range`、嵌套是 `别名:表!外键列(fields)`；且真实库有列默认值——`task_submissions.status` 缺 `DEFAULT 'submitted'` 会让「审核」按钮整块消失（假失败）。已全部在 stub 中补齐。
2. **Playwright 侧三项环境坑**：
   - Vite 默认只绑 `::1`，`127.0.0.1` 连不上 → 显式 `--host 127.0.0.1`；
   - 应用注册 PWA service worker，而 Playwright **不拦截 SW 处理的请求** → 必须 `serviceWorkers: 'block'`，否则 `page.route` 防线形同虚设（这是本轮排查耗时最多的一项，已由 `safety.spec.ts` 长期看护）；
   - 本地 `chromium-headless-shell` 下载失败 → 改用 `channel: 'chromium'`（完整 Chromium 的 headless 模式），少一个下载依赖、渲染更贴近真实浏览器。
3. **antd 可访问名两个陷阱**（已封进 `tests/e2e/helpers.ts` 的 `btn()`）：恰好两个汉字的按钮会被插入空格（`继续` → `继 续`）；带图标的按钮可访问名含图标名（`lock 修改密码`）。
4. **DatePicker 不能用回车提交**：输入框在 antd Form 内回车会触发表单隐式提交，弹窗在点击「发布」前就关闭 → 改为失焦提交。
5. **新记入 `docs/ISSUES.md` 的问题**：#9 任务详情弹窗状态不随审核刷新（建议 Phase 1 B5 处理）、#10 index.html 注释中 `%VITE_*%` 触发 Vite 警告。

### 本阶段对 Phase 1-4 的直接影响

### 数据库优化升级（第十七部分）做了什么

一次不改变任何业务语义的纯优化，全部幂等可重跑，**可在部署 v4.3.0 前端之前或之后执行**：

1. **`users.auth_id` 唯一索引**——RLS 的每条策略都要算 `auth_id = auth.uid()`，而该列此前**没有索引**，等于每次策略判定都全表扫描 users；这是登录后所有查询的公共开销。先查重再建唯一索引，有重复则退化为普通索引并 `RAISE NOTICE`，不会让整个脚本失败。
2. **外键索引补齐 22 条**——PostgreSQL 不会为外键列自动建索引；缺索引会让 FK 联表、以及 `ON DELETE CASCADE`（删任务级联删提交/里程碑）退化为全表扫描。
3. **复合索引 11 条**——贴合真实 `WHERE + ORDER BY`：通知分页 `(user_id, created_at DESC)`、未读部分索引、任务 `(assigned_department, status, created_at DESC)`、`(status, deadline)`、`updated_at` 周报窗口、公告/论坛时间线、票务开抢倒序、埋点模块维度等。
4. **`updated_at` 交给数据库触发器**（tasks / task_templates / forum_posts / department_guides / platform_guides）——此前由前端各调用点手写，绕过前端改数据时不更新，而周报「本周完成数」正是按 `updated_at` 圈时间窗。
5. **完整性收口**——`users.role`、`task_milestones.status` 两个取值完全枚举的列加 CHECK（`NOT VALID`：存量行不校验、只约束后续写入）。**有意不加**的列与原因已写在 SQL 注释里（`tasks.status`/`priority` 有历史取值且后续版本还会扩枚举；`notifications.type` 在 Phase 3 要加 `mention`，硬约束会让新功能写入失败）。
6. `ANALYZE` 刷新统计信息，并附核对查询语句。

1. **导出格式用 CSV 而非计划里写的 `xlsx`（安全决策，需知悉）**：npm 上 `xlsx`（SheetJS 社区版）最新版仍是 **0.18.5（2022-03-24 发布）**，带两个高危公告（GHSA-4r6h-8v6p-xvw6 原型污染、GHSA-5pgg-2g8v-p4x9 ReDoS），修复版只在 SheetJS 自建 CDN 分发、npm 侧永久停更——引入即等于接受两个没有升级路径的高危依赖。本轮三处导出都是扁平表格，CSV + UTF-8 BOM 完全满足「Excel/WPS 打开中文不乱码」的验收口径，且零依赖、零供应链风险。CSV 基座已做转义与**公式注入防护**（`= + - @` 开头前置单引号）。若后续确实需要多 sheet/样式，再单独评估 `write-excel-file`（MIT，4.1.1）。

6. **首次执行优化脚本报 `42P01 relation "users" does not exist`——以及我的一次误判（已修，值得记一笔）**：
   - **第一轮**：报未限定的 `users` 不存在。我判定为「SQL Editor 会话 `search_path` 不含 public」，于是加了 `SET search_path = public;` 并把所有表名改写成 `public.xxx`。
   - **第二轮（证伪）**：用户把表名限定成 `public.users` 后**仍然**报 `42P01 relation "public.users" does not exist`。这一条错误信息本身就是证据——**Postgres 只有在表确实不存在时才会对全限定名报此错**，所以「search_path 解释」是错的，真正原因是**SQL Editor 打开的是另一个 Supabase 项目**（Dashboard 会记住上次打开的项目，从历史记录进来很容易落到隔壁库）。
   - **交叉验证方式（可复用）**：用本地 `.env` 里的项目 URL 直接探测 REST 接口——`/rest/v1/users`、`/rest/v1/tasks` 都返回 **HTTP 200**（返回空数组是 RLS 拦掉了匿名行，属正常），证明表就在该项目 public schema 下，应用的库与「用户该贴的项目」是同一个。
   - **教训（两条，都比原来那条更硬）**：① 报错里带限定名时，不要往 `search_path` 上想——先确认**连的是不是同一个库**（`SELECT current_database()`），再谈 schema；② `public.` 前缀这条加固**保留**（零成本，且真能覆盖 search_path 异常的场景）。
   - **顺带确认无副作用**：错项目里什么都没被改——脚本第一条可执行语句就是那个查重 `DO` 块，它在第 3 行 `IF EXISTS` 即失败，后面 22 个外键索引、11 个复合索引、触发器、约束、`ANALYZE` 一条都没跑；`SET search_path` 只是会话级设置，不留痕。

### 偏差与关键决策

1. **二维码安全性落点（与计划的偏差已在第十八部分注释记录）**：计划写「短时效签名」，实现为**库内随机密钥 + md5 keyed hash + 15 分钟有效期**的 MAC 令牌；密钥由数据库随机生成存 `app_secrets`（对 anon/authenticated 完全封锁、不进仓库）。真正的边界在服务端：权限 + 时间窗（活动前 2 小时至后 6 小时）+ 幂等。
2. **扫码降级入口不是「补丁」而是产品的一部分**：E2E 环境无摄像头，且现场常见屏幕反光/亮度低。因此签到码原文**直接展示在二维码下方**（等宽、可选中、可复制），扫码与手输走同一个 RPC。这一条同时让 E2E 能覆盖完整签到链路。
3. **积分「只读」是刻意的**：`points_ledger` 是唯一不套用 `authenticated_full_access` 的业务表，前端只有 SELECT；配套两条防伪触发器（审核权、签到权收口到部门负责人及以上，放行 `service_role`）。
4. **stub 保真度又踩一课（值得记）**：`dev-stub` 的 `send()` 原本对字符串**原样输出**，而真实 PostgREST 对标量 RPC 返回的是**带引号的 JSON 字符串**。结果前端 `unwrap` 解析失败，报错信息里赫然就是那串令牌原文（`issueCheckInToken 查询失败 { error: "SUP1.…" }`），二维码一路显示「生成失败」。修复：`send` 一律 JSON 序列化（空串留给 201/204 无内容响应）。**教训：stub 与真实协议的差异，最先暴露在「解析失败」类错误里，而不是断言失败里。**
5. **首屏体积一度破预算，已修复（值得记一笔）**：新组件一进来，急加载 JS 从 319.5 KB gz 涨到 **380.3**（预算 340）。根因不在新代码量，而在分包启发式——rolldown 的 `entriesAware` 把带新组件名的 antd 块并进了「与入口共享」的块，而**入口是静态 import 它们的**，于是次要页面用的 antd 组件被算进首屏。试过把 4 个次要界面改 `React.lazy`：反而涨到 388（还多 4 个块），已回退。最终解法是把 `entriesAwareMergeThreshold` 从 40KB 降到 **8KB**，各入口保住自己的小块：**325.2 KB gz / 14 块**。反向数据：16KB→329.5、0KB→329.3、200KB→535.4（更糟）。同轮还发现二维码库被 `priority: 1` 的 vendor 兜底分组吸走（vendor 是急加载的），已加独立分组让它真懒加载。量法固化为 `scripts/measure-eager.mjs`，预算与旋钮说明写进 CLAUDE.md。

6. **antd 6 弃用清理顺带推进**：新代码发现 `Alert message` 已弃用 → 连同存量 4 处一并改为 `title`；`Drawer width` 弃用记录为 ISSUES #11（存量面较大，另开一轮）；`Modal width` 未弃用，无需改。ISSUES #2 因 `destroyOnClose` 与 `Alert message` 均已清零而移入「已修复」。

### 偏差与关键决策

1. **回复数/点赞数改「计数列 + 触发器」而不是每次 count**：计划只写「帖子卡点赞（乐观更新 + 计数）」。落地时发现原 `fetchPosts` 对每个帖子各发一条 `head: true` 的 count（一页 20 帖 = 1+20 次往返），既违反 CLAUDE.md 的性能铁律，又让「点赞数」无处安放。于是新增两个计数列由触发器维护，列表退化为单条查询——**这一步顺带把论坛列表的 N+1 彻底删掉了**。
2. **提及的通知方由前端解析，数据库不解析正文**：只有从成员候选面板点选过的成员才进 `mentionIds`。取舍理由见 CLAUDE.md（通知不是权限；Markdown 千变万化，触发器里解析必然不准）。
3. **`forum_likes` / `forum_bookmarks` 是本项目第一批按行 RLS 的表**：这是 Phase 4 C2 的试点。SELECT 放行全体登录用户，INSERT/DELETE 要求 `user_id = current_app_user_id()`，不建 UPDATE 策略。**代价是需要新的辅助函数**——直接复用第十八部分的 `current_app_user_id()`，没有引入新概念。
4. **旧头像的删除是「火后不理」**：attachments bucket 的删除策略限制「仅上传者本人」，换头像时删旧图失败也不影响新头像生效；不删的旧图留在 `avatars/{userId}/` 下，不会外泄。
5. **`onboarded` 的存量回填用固定时间字面量而非 `now()`**：迁移脚本要能重复执行，用 `now()` 会把「上次执行之后新注册的人」误标成已引导。前端读取用 `onboarded === false` 严格判断，避免老缓存（无此字段）导致升级瞬间全体老用户被弹一次。
6. **三个必须记的坑（都是本地 E2E 抓到的）**：
   - **弹窗表单不要在 `afterOpenChange` 里回填**：动画结束（约 300ms）后才 `setFieldsValue`，会把用户这段时间敲进去的内容覆盖掉——资料编辑就这么丢过一次输入（PATCH 请求里赫然是旧值）。改为「`{open && <Form/>}` 条件挂载 + `initialValues`」。
   - **stub 的 POST representation 必须回传「落库后的整行」**：旧实现只回传「请求体 + id/created_at」，缺 `TABLE_DEFAULTS` 补的列 → `users.onboarded`（DEFAULT false）在响应里是 `undefined` → 新人引导永远不弹。顺带修掉「多行插入时所有行的 id 都是最后一行的 id」。
   - **`fetchPosts` 的回复数断言必须用「造数据 + 计数」而不是「数种子回复」**：种子里的回复数会随别处用例变化，测试只断言「计数列 == 实际回复行数」。

### 偏差与关键决策

1. **C2 的范围判断：写侧全面收口，读侧有 5 张表刻意留宽**（与计划「逐表定义四类策略」的差异）。
   调研全部 `supabase.from()` 调用点后确认：`users`（通讯录读全员）、`tasks`（通讯录里的「他人任务计数」读全校）、
   `tickets` / `ticket_records`（人人都要算剩余票数）、`school_notices` 的读是**刻意的全量读取**。
   收紧它们不会报错，而是让页面**静默少数据**——比不收紧更危险。真收的前置改造（三个聚合 RPC）
   已写进 `docs/ISSUES.md` #14。**写侧没有让步**：改前任何登录用户直接打 REST 就能把自己写成 president、删光任务与公告。
2. **验证方式的转变（本阶段最重要的方法论收获）**。计划写「细粒度 RLS 在 E2E 就绪后执行，回归有保障」——
   实际落地时发现这个前提**不成立**：E2E 与单测打的是 dev-stub，而 stub 不实现 RLS，
   策略写错在自动化测试里**不会有任何反应**。于是补了一份角色冒充自证脚本（`supabase-verify-v4.6.0.sql`）：
   在事务里 `SET ROLE authenticated` + 注入 `request.jwt.claims` 冒充三种角色，
   逐条撞策略并断言「该放行的放行、该拒绝的拒绝」，`ROLLBACK` 收尾不留痕。
   细节上做了三处防御：`SET ROLE` 预检（不允许切换时降级为只跑结构核对并说明原因，不让脚本整体失败）、
   允许类探测一律用 `SET 列 = 列` 的无变化写法、退票探测针对**自造标记票券**而非真实数据。
3. **计划的「分两批上线（先读后写）」改为「一个脚本内先建后拆」**。读侧大部分有意保留，
   分两批既无对应内容、又要求用户跑两遍；真正的风险不是读/写混在一起，而是**「拆旧」早于「建新」
   会出现没有策略的真空期**（策略之间是并集，两套并存时权限仍是旧的宽松状态）。故顺序固定为
   先建新策略 → 最后统一摘掉 `authenticated_full_access`，并在文件头写明这条。
4. **顺手修掉三个 RPC 层的真实缺口**（都不在原计划里，属审计副产品）：
   - **anon 默认授权**：实测 anon key 直打 REST 可调 `role_level` / `is_organizer` / `semester_of` /
     `check_in_ticket` / `ticket_qr_token`（前三个直接返回数据）。根因是 Supabase 建库时对 public schema 有
     `ALTER DEFAULT PRIVILEGES … GRANT ALL ON FUNCTIONS TO anon`。已逐个 REVOKE，并取消这条默认授权，
     避免下一个人再踩。
   - **`grab_ticket` 的 `p_user_id` 完全由调用方决定**：匿名或任何登录用户都能拿别人的 id 抢票、消耗对方限购额度。
     已加「非 service_role 时只能替自己抢」的校验。
   - **注册的角色可自选**（见下条）。
5. **注册整体搬进 `register_user()`，`users` 表不再有 INSERT 策略**。原流程前端直插 users 且 `role` 由请求体带来——
   这条「只允许写自己」的策略看着无害，实际等于「任何人都能把自己注册成 president」。
   搬进函数后角色与部门**由邀请码推导**，核销与建号在同一事务同一行锁内完成
   （顺带修掉「两人同时用同一张码注册 → 都算成功但只 +1」的竞态，与 P0-01 抢票同一类问题）。
   **行为变更（需知悉）**：并发/过期场景下，注册从「码废了但人建出来了」变为**明确拒绝并提示原因**（学号不落库）。
6. **C3 的坑：懒加载页面上扫 a11y 会扫到上一页**。首跑把任务管理的问题记到了部门公告名下——
   点侧边栏后 URL 立刻变、新页面 JS 还在下载，此时 DOM 里仍是上一页。改用「整页 `goto('/#/xxx')` + 该页独有标题」
   做就绪锚点；**锚点不能用「发布任务」这类文案**（工作台快捷入口里也有，会在上一页就命中）。
7. **D1 的两个保命设计**：① **必须分页**——PostgREST 单次最多 1000 行，不分页的备份会「成功」地只备前 1000 行，
   这是最危险的失败（看起来成功了），故用 `Range` 翻页并以 `count=exact` 的总数**核对行数**，对不上直接退出；
   ② **不备份 `app_secrets`**（二维码签名密钥）——把密钥写进 git 历史等于长期泄露，恢复时重新生成即可。
   恢复脚本必须 `--yes` 才写库、先校验 sha256、按依赖序 upsert。
8. **`notice_reads` 补了一条缺失的 UPDATE 策略**（第八/九部分建的策略只有 SELECT+INSERT，
   而 `markNoticeRead` 用 upsert → 第二次读同一条公告会走 `ON CONFLICT DO UPDATE`，没有 UPDATE 策略时该分支报 RLS 错，
   前端只 log 不提示，表现为 `read_at` 不再刷新）。属补漏，不是加固。
