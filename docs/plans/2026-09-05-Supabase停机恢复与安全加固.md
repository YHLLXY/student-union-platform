### Dashboard 上看到的 error 是什么

观测页「Last 60 minutes」恰好覆盖暂停期与恢复瞬间，error 均为**停机窗口期的积压**，不是现存问题：

| --- | --- | --- |
| API Gateway | 28 | 暂停期间所有打到网关的请求返回 5xx（打开着的旧标签页在自动重试） |

## 二、恢复过程中发现的安全漏洞（本次修复主体）

实测（恢复当天、修复前）：

1. **匿名可读全库**：仅凭前端公开的 anon key 即可 `select=*` 拖走 users 全表（真实姓名/学号/部门/角色）——全员名单泄露，且姓名+学号正是找回密码的核验凭据，等同任意账号可被接管。
2. **匿名可写可删**：UPDATE/DELETE 探针（不存在的行）均返回 204，即任何人可篡改/删除任务、公告、论坛帖、抢票记录等任意业务数据。
3. 原因：`supabase-migration.sql` 第 183-215 行 users/tasks/notices/forum_posts/ticket_records 等表的 RLS 整段被注释停用，仅 platform_guides/notifications/notice_reads 三表开了 RLS；Supabase 对未开 RLS 的表默认授予 anon 全部权限。

## 三、修复设计

原则：**登录用户权限与现状完全一致（应用功能零变化），匿名一律拒绝。**

- 登录前必需的 3 条匿名查询改为 SECURITY DEFINER 函数（只做精确匹配、不可枚举）：
  - `validate_invite_code(code_input)` → 邀请码校验（注册页/教师注册页/找回密码）
  - `check_student_registered(student_id_input)` → 学号查重，只返回布尔
  - `verify_user_identity(name_input, student_id_input)` → 重置密码身份核验
- 14 张未开 RLS 的表：`ENABLE ROW LEVEL SECURITY` + 每表一条 `FOR ALL TO authenticated USING (true) WITH CHECK (true)` 策略。
- 前端 `authService.ts` 四个函数（checkInviteCode/checkTeacherCode/checkStudentId/verifyUser）改走 rpc；rpc 未创建（PGRST202）时回退旧直查——**SQL 与前端的执行顺序无关紧要，任何先后组合都不会打断线上功能**。
- stub 服务器（`scripts/dev-stub.mjs`）补齐 3 个 rpc，本地可完整回归。
