# v4.1 首屏性能优化实施计划

> 2026-09-05 · 目标：显著降低"打开慢"的体感，**保持现有视觉界面完全不变**
> 约束：不动 UI 设计；所有改动限于启动路径、分包策略、Service Worker、认证引导逻辑

---

## 一、诊断结论（全部基于实测，非推测）

### 实测环境
线上地址 `https://yhllxy.github.io/student-union-platform/`，受控 Chromium：

| 场景 | 数据 |
|------|------|
| **冷加载**（首次访问） | TTFB 479ms → DCL 2105ms → **FCP 2268ms**；总传输 **434KB (压缩后)** |
| **热加载**（SW 已接管，所有资源命中缓存，0 字节走网络） | **仍等 714ms** 才拿到 HTML（DCL 834ms） |
| chunk 构成 | 两个 antd 块合计 **214KB gz（占 49%）**；vendor 含 @dnd-kit（仅任务页使用） |

### 根因 1：SW 对 HTML 用"网络优先"，热加载白等一轮网络
`public/sw.js` 导航请求策略为网络优先+回退缓存。后果：**已安装 PWA 每次打开都强制等一次 github.io 完整往返**（本机实测 714ms；国内网络常见 2-5s），而完美可用的缓存副本就在本地。这是"每次打开都慢"的最大元凶。

### 根因 2：登录页关键路径携带全量 antd 壳层
`App.tsx` 静态导入 `AppLayout` → 连带 NotificationBell / GlobalSearch / GuideDrawer / FeedbackModal / PwaInstallButton 全部进入入口静态图。sourcemap 审计确认 `antd~index-CyWbnMeV`（87.5K gz，仅入口使用的 antd 组件）内含 dropdown 24K / drawer 21K / badge 27K / avatar 13K / select 42K / input-number 19K / popconfirm 9K / modal 49K（DevEntryModal）——**全部是登录后才用到的组件**。

### 根因 3：vendor 组"一人急加载、全组陪绑"
`@dnd-kit` 仅被 tasks 模块引用，但与 react-router / @tanstack（急加载）同在 `vendor` 组 → 整块 37.8K gz 变成急加载。

### 根因 4：motion 整包急加载，但急加载链路零使用
main.tsx 静态导入 `LazyMotion + domAnimation`；已核实 App/AppLayout/LoginPage/ErrorBoundary/SkeletonBlocks 等急加载文件**没有任何 motion 组件调用**。82KB 原始 / 29K gz 中绝大部分（domAnimation 特性集）可延后。

### 次要因素
- App.tsx 在 `getCurrentUser()`（Supabase users 表 SELECT，一次网络往返）返回前**不渲染任何内容**——已登录用户每次打开都多等 200ms~1s+（supabase 地域相关）。
- supabase 域名无 preconnect，首个 API 请求要现场建连（DNS+TCP+TLS）。
- version.json 检查请求与关键资源抢带宽（小，顺手延后）。

## 二、方案（P0 四项 + P1 两项）

### P0-1 SW 导航策略：网络优先 → stale-while-revalidate（收益最大）

**参考**：[Workbox 缓存策略](https://developer.chrome.com/docs/workbox/caching-strategies-overview)——SWR 语义为"立即回缓存 + 后台静默更新"；SPA 场景业界共识是用预缓存的 app shell 服务导航请求，更新通过版本机制提示。

改动（`public/sw.js` + `index.html`）：
1. 导航请求：`caches.match` 命中立即返回，同时 `fetch` 后台更新缓存；未命中走网络。
2. **旧资源保护**（关键正确性设计）：缓存了旧 HTML 的会话，其引用的旧 hash 资源必须仍可用。activate 清理策略从"删光旧缓存"改为"**保留最近 2 代**"（app-shell/app-assets 各按代数排序，仅删除更早的），防止"旧 HTML 引用已被清空的旧资源 → 白屏"。
3. **更新确定性**：用户点击"新版本已就绪"toast → `skipWaiting` → 新 SW 接管（controllerchange）→ 主线程 `postMessage({type:'PURGE_ALL'})` → 新 SW 清空全部缓存 → `location.reload()` → 网络拿全新 HTML+资源。更新语义与现在一致（点击后必见新版），且比现在更可控。
4. `version.json` 请求直接放行（不 respondWith、不入 assets 缓存）——它带 `?t=` 唯一查询串，现状会造成 assets 缓存按版本检查次数无限堆积。

### P0-2 急加载瘦身（目标：434KB gz → ≤340KB gz）

a. **懒壳层**：`App.tsx` 改 `const AppLayout = lazy(() => import('@/components/AppLayout'))`，`<Suspense fallback={<RouteSkeleton />}>` 包裹。整棵壳层子树（含 5 个壳层组件与其 antd 组件）移出登录页关键路径。已登录用户本就先见 RouteSkeleton（等 Supabase 查询），加载语法与现状一致，仅更快。
b. **DevEntryModal 懒加载**：登录页内 `lazy(() => import('./DevEntryModal'))`，把 modal 模块（49K 原始）移出关键路径。
c. **motion 特性异步化**：main.tsx `features={() => import('@/components/motion/features').then(r => r.domAnimation)}`（新增 `src/components/motion/features.ts` 一行转发导出）。首帧后首个 m 组件渲染前特性早已就绪（路由 chunk 加载 ≥ 数百 ms），strict 模式安全。**验证门禁**：构建后若 motion 急加载体积未明显下降（tree-shaking 未拆开），回退此条。
d. **@dnd-kit 独立分组**：vite.config.ts codeSplitting 增 `{ name: 'dnd', test: /node_modules[\\/]@dnd-kit[\\/]/, priority: 7 }`（高于 vendor 的 1 即可，与 antd/motion 测试无交集）。

### P0-3 认证快速路径（已登录用户免阻塞）

- `authService` 拆出 `getLocalSession()`（`auth.getSession`，纯本地读）与 `fetchProfileByAuthId()`；`getCurrentUser()` 保留原语义。
- App.tsx 引导逻辑：
  1. 无 session → 直接登录页（本就快，保持）；
  2. 有 session 且 localStorage 有**同 auth_id** 的缓存档案 → 立即渲染，后台拉新档案静默校正（角色变更等），成功后回写缓存；
  3. 有 session 无缓存 → 现状阻塞拉取。
- 缓存写入点：后台刷新成功、`onLoginSuccess`。清除点：SIGNED_OUT（连带 `queryClient.clear()` 已有）。
- `index.html` 加 `<link rel="preconnect" href="%VITE_SUPABASE_URL%" crossorigin>`（Vite HTML 常量替换，[官方文档](https://vite.dev/guide/env-and-mode)确认；未定义时字面保留、无害）。省去首个 API 请求的建连时间。

### P1-4 version.json 检查延后

index.html 的 `checkVersion()` 从"SW 注册即拉"改为注册后 3s 延迟，避开冷启动关键期。`registration.update()` 10 分钟轮询不变。

### P1-5 发版链同步

package.json / version.json / sw.js CACHE_VERSION → **4.1.0**（发版铁律）。

## 三、明确不做（视觉不变边界）

- 不改任何页面/组件的视觉与交互，只动加载方式与启动时序；
- 不引入新依赖（不加 workbox，手写 SW 继续演进）；
- 不动 Dashboard/登录页布局、不动主题系统；
- `notification`（antd）保留急加载——useVersionNotification 需要它，收益小、迁移成本不值；
- React 19 / antd 6 / Vite 8 版本不动。

## 四、风险与回退

| 风险 | 缓解 | 回退 |
|------|------|------|
| SWR 旧 HTML + 被清资源 → 白屏 | 保留 2 代缓存 + 点击更新时先清后刷 | SW 导航策略一行改回网络优先 |
| 懒壳层首挂载闪骨架 | 与现状加载语法一致（现状等 Supabase 更久） | 改回静态导入 AppLayout |
| 缓存档案过期（角色被改） | 后台拉取静默校正；auth_id 键控防串号 | 删除缓存读取分支 |
| motion 异步特性加载竞态 | strict 下 m 组件仅存在于懒路由，首次渲染远晚于特性就绪 | 回退静态导入（验证门禁不达标时） |
| 构建环境无 VITE_SUPABASE_URL | href 字面保留，无功能影响 | 删除该 link 标签 |

## 六、审查记录（2026-09-05，逐条对照代码核实）

**核实通过的关键事实**：
1. `App.tsx:6` 静态导入 AppLayout，且 App.tsx 是其唯一引用方 → 懒壳层安全；
2. GlobalSearch / FeedbackModal / PwaInstallButton 仅被 AppLayout 引用，GuideDrawer / NotificationBell 经 barrel 被 AppLayout 引用 → 随壳层整体变懒；
3. `LoginPage.tsx:14` 静态导入 DevEntryModal（唯一入口），LoginPage 自身无 antd Modal 直接依赖 → DevEntryModal 可懒；
4. `getCurrentUser` 唯一调用方 App.tsx:36 → 拆分重构不影响他人；
5. `UserProfile` 含 `auth_id` 字段 → 缓存可按 auth_id 键控；
6. motion 官方类型 `features: FeatureBundle | LazyFeatureBundle`（framer-motion/dist/index.d.ts:555，注释示例即 `() => import(...)`）→ 异步特性为官方支持；
7. 急加载文件（App/AppLayout/LoginPage/ErrorBoundary/SkeletonBlocks/useVersionNotification）grep 确认零 motion 组件调用。

**审查中发现并修正的设计问题**：
- **修正 1（重要）**：SWR 不能按"当前 URL 匹配缓存"实现——用户首次可能从 `/` 进入而预缓存键是 `/index.html`，会静默脱靶。改为**所有导航一律服务预缓存的 shell 键**（即 Workbox `NavigationRoute`/`createHandlerBoundToURL` 的手写等价物），后台更新也固定写回 shell 键，杜绝键不一致。
- **修正 2（重要）**：`controllerchange` 在**首次访问**（新 SW `clients.claim()` 接管）时也会触发，若在此无条件 reload 会造成首次访问多刷一次。增加 `pendingActivate` 标志，仅在用户点击更新 toast 后的 controllerchange 才执行"清缓存 + 刷新"。
- 修正 3：保留 2 代的版本排序必须数字感知（`v4.10.0` 与 `v4.9.0` 的字典序陷阱），用 `localeCompare(…, { numeric: true })`。
- 修正 4：确认现有 bug——`version.json?t=` 每次唯一查询串会被 assets 缓存按"网络失败回退→put"路径无限堆积条目，本次一并修复（version.json 完全绕过 SW）。
- 澄清：App.tsx 的会话监听直接用 `supabase.auth.onAuthStateChange`（非 authService 导出的包装），authService 导出的 `onAuthStateChange` 每次事件都会查库但当前无人调用，本次不动它。

**结论**：计划与代码事实一致，按修正后方案执行。
