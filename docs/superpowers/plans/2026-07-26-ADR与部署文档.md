**Files:**
- Create: `docs/architecture-decisions/ADR-001-Supabase选型.md`

- [ ] **Step 1: 创建文件**

（先创建目录：`mkdir docs\architecture-decisions`）

```markdown
# ADR-001: 选择 Supabase 作为后端平台

- **状态:** 已采纳
- **日期:** 2025-06（项目启动时）
- **决策者:** 余翰林（独立开发者）

## 上下文

学生会交流平台需要一个后端来存储用户数据、任务、公告、票务等信息。作为单人项目，需要选择一个能快速开发、零运维的后端方案。

评估的方案：
1. **Firebase**（Google）— Firestore 数据库 + Auth
2. **Supabase**（开源）— PostgreSQL + Auth + Storage + Realtime
3. **自建后端**（Node.js + Express + PostgreSQL）

## 决策

选择 **Supabase**。

## 理由

| 维度 | Supabase | Firebase | 自建 |
|------|----------|----------|------|
| 数据库 | PostgreSQL（关系型，SQL） | Firestore（NoSQL） | 自己搭 |
| 免费额度 | 500MB 数据库 + 50K 月活 | 有免费层 | 需要服务器 |
| 实时通知 | Realtime（WebSocket） | Firestore 自带 | 需要 WebSocket 服务 |
| 学习成本 | 会 SQL 就行 | 需要学 Firestore 查询语法 | 需要学 DevOps |
| 迁移成本 | 标准 PostgreSQL，随时导出 | 被 Google 锁定 | 完全控制 |

核心考量：
- 本项目数据模型是**典型的关系型**（用户-部门-任务-公告），PostgreSQL 天然适合，NoSQL 反而别扭
- 单人项目没有运维能力，BaaS（Backend as a Service）是唯一现实选择
- Supabase 的 Realtime 功能（WebSocket 订阅数据库变更）让通知系统几乎零代码实现
- PostgreSQL 是行业标准，即使未来不用 Supabase，数据迁移到其他 PG 服务也简单

## 后果

### 正面
- 数据库 + 认证 + 存储 + 实时通知，一个平台全搞定
- 免费额度对 50-200 人的学生会完全够用
- SQL 让复杂查询（如工作看板聚合统计）变得简单

### 负面
- 网络延迟：Supabase 免费版服务器在海外（美西/新加坡），国内访问偶尔慢
- 冷启动：免费版数据库 7 天不活动会休眠，首次请求需要 ~2 秒唤醒
- RLS（行级安全）配置不正确可能导致数据泄露——需要仔细验证

### 缓解措施
- PWA Service Worker 缓存策略（network-first）掩盖部分延迟
- 数据看板页面（/admin 的分析 Tab）定期访问保持数据库活跃
```

### Task 2: ADR-002 — PWA 选型

**Files:**
- Create: `docs/architecture-decisions/ADR-002-PWA选型.md`

- [ ] **Step 1: 创建文件**

```markdown
# ADR-002: 选择 PWA 作为客户端形态

- **状态:** 已采纳
- **日期:** 2025-06（项目启动时）
- **决策者:** 余翰林（独立开发者）

## 上下文

学生会成员使用手机为主。需要一个能在手机上"像 App 一样"使用的方案。

评估的方案：
1. **React Native / Flutter** — 原生 App
2. **微信小程序** — 国内最流行的轻应用方案
3. **PWA**（Progressive Web App）— 网页应用 + Service Worker + 可安装

## 决策

选择 **PWA**。

## 理由

| 维度 | PWA | 小程序 | 原生 App |
|------|-----|--------|----------|
| 开发成本 | 和写网页一样 | 需要学 WXML/WXSS | 需要学 RN/Flutter |
| 分发 | 网址即用，无需审核 | 需要微信审核 | 需要应用商店上架 |
| 更新 | 刷新即更新 | 审核周期 1-7 天 | 审核周期 1-3 天 |
| 离线能力 | Service Worker 缓存 | 有限 | 可以 |
| 推送通知 | Web Push（iOS 17.4+ 才支持） | 订阅消息 | 原生推送 |

核心考量：
- **更新频率：** 学生会平台频繁迭代（v1 → v3.2），每周几次更新。小程序/App 审核周期会严重影响响应速度
- **维护负担：** 单人开发，维护三套代码（Web + iOS + Android）不可行
- **分发：** 二维码发到微信群 → 浏览器打开 → 添加到主屏幕，比"去应用商店下载"简单得多
- **iOS 安装：** iOS 17.4 起 Safari 支持 PWA 安装提示，之前的版本需要用户手动"添加到主屏幕"

## 后果

### 正面
- 一套代码跑所有平台（PC + iOS + Android）
- 更新即时生效，不需要审核
- Service Worker 离线缓存让基本功能在没有网络时也能打开

### 负面
- iOS Safari 对 PWA 的支持不如 Android Chrome 完善（如 Web Push 直到 iOS 17.4 才支持）
- 微信内置浏览器不会触发 PWA 安装提示，需要引导用户用系统浏览器打开
- 不能用原生硬件功能（蓝牙、NFC等）——但学生会平台不需要

### 缓解措施
- `index.html` 中保留 `beforeinstallprompt` 兜底 + 手动安装按钮
- 使用指南中指导用户用 Safari/Chrome 打开并添加到主屏幕
```

# ADR-003: 选择 React + TypeScript + Ant Design + Vite

- **状态:** 已采纳
- **日期:** 2025-06（项目启动）+ 2026-07（重大重构）
- **决策者:** 余翰林（独立开发者）

## 上下文

项目经历了两次重大技术选型变更：

- **v1（2025-06 ~ 2026-06）：** jQuery + HTML + CSS，纯静态页面。快速原型，给学生会的学长看效果。
- **v2（2026-07）：** 全量重写为 React 19 + TypeScript 6 + Ant Design 6 + Vite 8 + Supabase。原因：v1 的代码已经无法维护（大量重复 DOM 操作，无状态管理，无类型检查）。

## 决策

| 技术 | 选择 | 替代方案 | 理由 |
|------|------|----------|------|
| 框架 | React 19 | Vue, Svelte | 生态最大，Ant Design 绑定 React |
| 类型 | TypeScript 6 | JavaScript | Supabase 返回类型复杂，无类型极易出 Bug |
| UI 库 | Ant Design 6 | Material UI, shadcn/ui | 中文企业级生态最好，Table/Form/Modal 开箱即用 |
| 构建 | Vite 8 | webpack, CRA | 开发服务器秒启动，HMR 快 |
| 后端 | Supabase | Firebase, 自建 | 见 ADR-001 |

## 后果

### 正面
- TypeScript 在编译期捕获了数十个潜在 Bug（特别是 Supabase 返回值的类型转换）
- Ant Design 的 Table/Form/Select/DatePicker 大幅减少手写 UI 代码
- Vite 的开发体验远超 webpack（1 秒 vs 30 秒启动）

### 负面
- Ant Design 6 的 bundle 较大（~200KB gzipped），首屏加载需要优化
- React 的学习曲线对继任者有挑战
- TypeScript 的严格类型检查在开发中偶尔让人沮丧——但换来了运行时安全

### 缓解措施
- `React.lazy()` + `Suspense` 分包加载，减少首屏体积
- PWA Service Worker 缓存让二次访问几乎秒开

- [ ] **Step 2: 创建 ADR-004（RLS 策略决策）**

```markdown
# ADR-004: 暂缓启用全部 RLS——使用应用层权限控制

- **状态:** 已采纳（可重新讨论）
- **日期:** 2025-06（初始决策），2026-07（重新评估）
- **决策者:** 余翰林（独立开发者）

## 上下文

Supabase 推荐使用 RLS（Row Level Security）作为数据库安全层。项目早期写了 RLS 策略但全部注释掉了（见 `supabase-migration.sql` 第四部分），实际使用应用层权限模型（`hasMinRole()` + 前端查询过滤）。

2026-07 重新评估后，决定**暂缓全面启用 RLS**，但**对特定高价值表启用**。

## 决策

**分阶段启用 RLS：**

| 表 | RLS 状态 | 原因 |
|----|----------|------|
| `notifications` | ✅ 已启用 | 用户只能读自己的通知，几乎无副作用 |
| `notice_reads` | ✅ 已启用 | 用户只能创建自己的已读记录 |
| `platform_guides` | ✅ 已启用 | 只读公开，管理写受限 |
| `usage_events` | ❌ 未启用 | 只通过 `trackEvent()` 匿名写入，无读权限需求 |
| `users` / `tasks` / `notices` / `forum_posts` / `forum_replies` / `tickets` / `ticket_records` | ❌ 未启用（注释） | 见下方理由 |

**不启用全面 RLS 的理由：**

1. **部门权限不够简单：** RLS 策略中 `department = (SELECT department FROM users WHERE auth_id = auth.uid())` 这种子查询在小数据量（50-200人）下没问题，但"主席看全校""协作部门看跨部帖子"等场景让策略迅速复杂化。策略越复杂，写出安全漏洞的概率越高。

2. **单人项目，前端是唯一的数据库消费者：** 没有第三方 API 直接查数据库。所有查询都经过 `src/modules/*/xxxService.ts` 层过滤。只要 service 层的 `hasMinRole()` 过滤正确，数据库层 RLS 就是重复的。

3. **Supabase 的 anon key 已公开在 JS bundle 中：** 即使启用 RLS，攻击者拿到 anon key 后仍能以已登录用户身份调 API。RLS 只限制"同角色的用户不能看其他部门数据"，不防"恶意用户用自己账号爬数据"。对于学生会平台，风险可接受。

4. **RLS 策略调试困难：** 策略写错 → 用户看不到数据 → 很难排查是前端 Bug 还是 RLS 拦截。Supabase Dashboard 没有 RLS 调试工具。

## 后果

### 正面
- 应用层权限逻辑集中在 `hasMinRole()` + service 函数中，一处修改全局生效
- 不受 RLS 限制，管理员可以灵活查询跨部门数据

### 负面
- 如果未来有人写了一个新的 service 函数忘记加权限过滤 → 数据可能泄露
- 如果 Supabase anon key 泄露 → 攻击者可以以任意已登录用户的身份调 API

### 缓解措施
- 所有 service 函数遵循统一模式（见 `src/modules/tickets/ticketService.ts`）
- 对敏感操作（如抢票）使用 RPC + `SECURITY DEFINER` 而非直接操作表
- 如果项目将来用户量增长到 >1000 人或向外校开放，应重新评估全面启用 RLS
```

## 三、从零部署（30 分钟）

### 3.1 Fork 项目到你的 GitHub

1. 打开 https://github.com/yhllxy/student-union-platform
2. 点击右上角 **Fork** → **Create fork**
3. 等几秒钟，项目就复制到你的账号下了

### 3.2 创建 Supabase 项目

1. 登录 [supabase.com/dashboard](https://supabase.com/dashboard)
2. 点击 **New project**
3. 填写：
   - Name: `student-union`（随便写）
   - Database Password: **设置一个你记得住的密码**（重要！）
   - Region: 选 **West US** 或 **Singapore**（离中国最近）
4. 点击 **Create project**，等 2 分钟让数据库启动

### 3.3 执行数据库迁移

1. 在 Supabase Dashboard 左侧菜单 → **SQL Editor**
2. 点击 **New query**
3. 打开本项目 `supabase-migration.sql` 文件，**全选复制**
4. 粘贴到 SQL Editor，点击 **Run**
5. 看到 "Success" 就完成了

### 3.4 创建存储桶

1. Supabase Dashboard 左侧 → **Storage**
2. 点击 **New bucket**
3. Name: `attachments`
4. ✅ 勾选 **Public bucket**
5. 点击 **Create bucket**

### 3.5 获取 API 密钥

1. Supabase Dashboard 左侧 → **Settings** → **API**
2. 记下两个值：
   - **Project URL**（类似 `https://xxx.supabase.co`）
   - **anon public key**（很长一串，以 `eyJ` 开头）

### 3.6 配置 GitHub Actions 自动部署

1. 打开你 Fork 的 GitHub 仓库 → **Settings** → **Secrets and variables** → **Actions**
2. 点击 **New repository secret**，添加以下 3 个：

| Name | Value |
|------|-------|
| `VITE_SUPABASE_URL` | 你的 Project URL（第 3.5 步） |
| `VITE_SUPABASE_ANON_KEY` | 你的 anon key（第 3.5 步） |
| `VITE_DEV_KEY` | 一个你自己定的开发者密钥（比如 `MYDEV2026`） |

3. GitHub 仓库 → **Actions** 标签 → 启用 Workflows
4. 随便改点东西推送（或手动触发 Action），首次部署开始

### 3.7 设置 GitHub Pages

1. GitHub 仓库 → **Settings** → **Pages**
2. Source: **GitHub Actions**
3. 保存

部署完成后，访问 `https://你的用户名.github.io/student-union-platform/` 就能看到平台了。

## 六、常见问题

### Q: 注册时说"邀请码无效"
A: 检查 `invite_codes` 表 → 该邀请码的 `is_used` 是否为 `true`，`max_uses` 是否已用完，`expires_at` 是否已过期，`revoked_at` 是否不为空。

### Q: 上传文件失败
A: 检查 Supabase Storage → `attachments` bucket 是否存在且为 Public。

### Q: 通知收不到
A: 浏览器需要 HTTPS 才能用 Service Worker 和 WebSocket（本地 `localhost` 除外）。确保访问的是 `https://...github.io/...`。

### Q: 页面打开很慢
A: Supabase 免费版数据库 7 天不活动会休眠。首次访问需要等 ~2 秒。之后 PWA 缓存生效，速度正常。

### Q: 想加新功能
A: 参考 `docs/superpowers/specs/` 下的设计文档，在 `src/modules/` 下新建文件夹，复用现有 service 模式。改完后记得更新 `supabase-migration.sql`（如果加了表）。
