# P0-04 邀请码机制增强 实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 为 `invite_codes` 表增加 `max_uses`（最大使用次数）、`used_count`（已用次数）、`expires_at`（过期时间）、`created_by`（创建者）、`revoked_at`（撤销时间）五个字段，支持"一码多用"和"邀请码过期"，同时保持与现有 `is_used` 模式的完全向后兼容。

**Architecture:** 数据库 DDL 使用 `ADD COLUMN IF NOT EXISTS` 安全迁移，默认值确保旧数据不丢失。前端 `checkInviteCode()` 增加客户端二次校验（时间/次数/撤销），形成"数据库 RLS + 客户端兜底"双重保障。管理工作台增加 max_uses、expires_at 配置入口。

**Tech Stack:** PostgreSQL DDL + TypeScript + Ant Design DatePicker

## 风险评估与危险预案

| 风险 | 严重度 | 预案 |
|------|--------|------|
| 旧邀请码（seed 数据）没有 `max_uses`/`used_count` 值 | 🔴 高 | DDL 用 `DEFAULT 1` / `DEFAULT 0`，执行 ALTER TABLE 后所有旧行自动填充默认值。旧 `is_used=false` 的码 → `used_count=0 < max_uses=1` 仍然可用。旧 `is_used=true` 的码 → 如果 used_by 不为空，应该把 used_count 回填为 1 |
| `deactivateInviteCode()` 原来设 `is_used=true`，现在设 `revoked_at=now()`，但旧逻辑把 `is_used=true` 当作"停用" | 🟡 中 | `InviteCodeManage.tsx` 的状态判断从 `{!record.is_used && ...}` 改为 `{!record.revoked_at && record.used_count < record.max_uses && ...}`。需要仔细审查所有判断 `is_used` 的地方 |
| 旧 seed 数据停用码（`is_used=true, used_by=null`）与新机制不兼容 | 🟡 中 | DDL 回填时：如果 `is_used=true AND used_by IS NULL` → 说明是手动停用 → 设 `revoked_at=created_at` |
| `DatePicker` 组件引入新依赖（dayjs 类型） | 🟢 低 | Ant Design 的 DatePicker 本身就依赖 dayjs，`InviteCodeManage.tsx` 已经在 Ant Design 上下文中运行，无额外引入 |
| 邀请码校验逻辑变复杂，容易漏判 | 🟡 中 | 校验顺序固定：revoked_at → expires_at → max_uses/used_count → is_used（兜底）。先检查最明确的失效条件 |

```sql
-- ============================================================
-- 第十五部分：邀请码机制增强（P0-04）
-- ============================================================

-- 1. 新增字段（向后兼容，DEFAULT 确保旧数据不丢失）
ALTER TABLE invite_codes ADD COLUMN IF NOT EXISTS max_uses INTEGER DEFAULT 1;
ALTER TABLE invite_codes ADD COLUMN IF NOT EXISTS used_count INTEGER DEFAULT 0;
ALTER TABLE invite_codes ADD COLUMN IF NOT EXISTS expires_at TIMESTAMPTZ;
ALTER TABLE invite_codes ADD COLUMN IF NOT EXISTS created_by UUID REFERENCES users(id);
ALTER TABLE invite_codes ADD COLUMN IF NOT EXISTS revoked_at TIMESTAMPTZ;

-- 2. 数据回填：旧"已使用"的邀请码设 used_count = 1
UPDATE invite_codes
SET used_count = 1
WHERE is_used = true
  AND used_by IS NOT NULL
  AND used_count = 0;

-- 3. 数据回填：旧"手动停用"的邀请码（is_used=true 但 used_by 为空）→ 视为被撤销
UPDATE invite_codes
SET revoked_at = created_at
WHERE is_used = true
  AND used_by IS NULL
  AND revoked_at IS NULL;

-- 4. 索引：按创建者查询
CREATE INDEX IF NOT EXISTS idx_invite_created_by ON invite_codes(created_by);
```

```typescript
/** 生成邀请码 */
export async function generateInviteCode(
  department: string,
  role: string,
  maxUses: number = 1,
  expiresInDays: number | null = null,
  createdBy: string | null = null,
): Promise<string | null> {
  const code = Math.random().toString(36).substring(2, 8).toUpperCase();
  const expiresAt = expiresInDays
    ? new Date(Date.now() + expiresInDays * 24 * 60 * 60 * 1000).toISOString()
    : null;

    .from('invite_codes')
    .insert({
      code,
      department,
      role,
      max_uses: maxUses,
      used_count: 0,
      expires_at: expiresAt,
      created_by: createdBy,
    });

  if (error) { log.error('generateInviteCode 生成失败', error); return null; }
  return code;
}
```

```typescript
/** 检查邀请码是否有效（数据库查询 + 客户端二次校验） */
export async function checkInviteCode(code: string) {
  const { data, error } = await supabase
    .from('invite_codes')
    .select('*')
    .eq('code', code)
    .single();

  if (error || !data) return null;

  // 客户端二次校验（数据库 RLS 不保证业务规则）

  // 1. 已被撤销
  if (data.revoked_at) {
    console.warn('[auth] 邀请码已被撤销:', code);
    return null;
  }

  // 2. 已过期
  if (data.expires_at && new Date(data.expires_at) < new Date()) {
    console.warn('[auth] 邀请码已过期:', code, data.expires_at);
    return null;
  }

  // 3. 已用完
  const usedCount = data.used_count ?? (data.is_used ? 1 : 0);
  const maxUses = data.max_uses ?? 1;
  if (usedCount >= maxUses) {
    console.warn('[auth] 邀请码已用完:', code, usedCount, '/', maxUses);
    return null;
  }

  return data;
}
```

**关键设计：** `usedCount >= maxUses` 替代了原来的 `eq('is_used', false)` 查询条件。旧的 `is_used` 字段保留但不再作为唯一判断标准——`is_used` 仅在 `used_count` 为 0 且 `max_uses` 未设置时充当兜底。

```typescript
/** 检查教师邀请码是否有效（role=teacher） */
export async function checkTeacherCode(code: string) {
  const { data, error } = await supabase
    .from('invite_codes')
    .select('*')
    .eq('code', code)
    .eq('role', 'teacher')
    .single();

  if (error || !data) return null;

  // 同样做客户端二次校验
  if (data.revoked_at) return null;
  if (data.expires_at && new Date(data.expires_at) < new Date()) return null;
  const usedCount = data.used_count ?? (data.is_used ? 1 : 0);
  const maxUses = data.max_uses ?? 1;
  if (usedCount >= maxUses) return null;

  return data;
}
```

- [ ] **Step 3: 更新 signUp() 中标记邀请码的逻辑**

在 [authService.ts:79-83](src/modules/auth/authService.ts#L79-L83)，原来标记邀请码的代码是：

```typescript
await supabase
```

替换为（在 `signUp` 函数内）：

```typescript
// 3. 标记邀请码使用（used_count + 1）
// 先用 SELECT 获取当前 count，再用 UPDATE 增加（客户端递增，非原子——但注册是低频操作）
const { data: currentCode } = await supabase
  .from('invite_codes')
  .select('used_count, max_uses')
  .eq('code', inviteCode)
  .single();

const newCount = (currentCode?.used_count ?? 0) + 1;
const maxUses = currentCode?.max_uses ?? 1;

await supabase
  .from('invite_codes')
  .update({
    used_count: newCount,
    is_used: newCount >= maxUses,
    used_by: userData.id,
  })
  .eq('code', inviteCode);
```

**注意：** 这里用了客户端递增而非数据库原子 `used_count + 1`。原因是 Supabase 不支持 `UPDATE ... SET used_count = used_count + 1` 通过 postgrest-js（需要 RPC）。注册是极低频操作（每天几次），并发冲突概率可忽略。如果未来需要原子化，可在 P1-05（注册流程事务化）中一并解决。
