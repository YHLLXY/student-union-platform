# 构建优化与代码分割（Vite 8 / Rolldown）

> v4.0 迭代调研沉淀 · 2026-09-03
> 结论均已在本项目 node_modules 的 rolldown 类型定义中逐字验证（比博客更可靠）。

## 一、背景：v3.6 的 801KB 怪物 chunk

用 `vite build --sourcemap` + sourcemap `sourcesContent` 字节统计可以精确解剖任意 chunk。v3.6 基线审计结果：

| Chunk | 体积 | 实际内容 |
|---|---|---|
| `SkeletonBlocks-*.js` | **801KB** | react-dom(533KB源) + antd 核心(450KB源) + 整个 Supabase SDK |
| `index-*.js` | 448KB | antd 另一半 + react-router + motion-dom(235KB源) + framer-motion |
| `TrophyOutlined-*.js` | 152KB | antd Table + Tree（以图标组件命名） |

**根因**：Vite 8 内置 Rolldown 后 `manualChunks` 已不被支持，自动分包把「入口 + 所有懒加载页共享」的 vendor 归并进以首个共享模块命名的 chunk（SkeletonBlocks 是被引用最多的业务模块）。vendor 撕成三块、命名错乱、哈希不稳定导致缓存全灭。

## 二、Rolldown 正确的分包 API

### 版本演进（重要）

| 时期 | API | 状态 |
|---|---|---|
| Rollup 时代 | `output.manualChunks` | Rolldown **不支持**（[rolldown-vite#119](https://github.com/vitejs/rolldown-vite/issues/119) 官方确认不会支持） |
| Rolldown 早期 | `output.advancedChunks` | 已标记 `@deprecated`（本机 rolldown 类型：*"Please use codeSplitting instead"*） |
| **Vite 8 正解** | **`output.codeSplitting.groups`** | ✅ 现行 API |

配置入口：`build.rolldownOptions.output.codeSplitting`（vite.config.ts）。

### `CodeSplittingGroup` 字段（本机 rolldown 5.x 类型定义）

```ts
{
  name: string,              // chunk 名，产物为 name-[hash].js
  test?: string | RegExp,    // 模块匹配。⚠️ Windows 正则必须用 [\\/] 匹配路径分隔符
  priority?: number,         // 高优先级组先匹配，命中模块从其他组移除；同优先级按索引
  minSize?: number,          // 组累计体积 < minSize 则整组放弃（回落自动分包）
  maxSize?: number,          // 组超限时按接近该值继续裂分
  minShareCount?: number,    // 被多少个入口共享才捕获，默认 1
  entriesAware?: boolean,    // ★ 按「引用入口集合」裂解子组（见下）
  entriesAwareMergeThreshold?: number,  // 小子组回并阈值（字节）
  includeDependenciesRecursively?: boolean, // 默认 true，减少循环 chunk
  tags?: ['$initial'],       // 仅捕获首屏静态依赖链
}
```

### entriesAware：本项目最关键的一个开关

默认 `false` 时组内模块合并成单个 chunk，**每个用到它的入口都要整块加载**。开 `true` 后按「哪些入口实际引用」聚成子组：

- 全站共享的 antd 核心 → `antd~index~…`（一个块）
- 只有部分页面用的 Table/DatePicker/Tree → `antd~MemberManage~DashBoardPage` 等独立子块
- 小子组按 `entriesAwareMergeThreshold`（本项目 40KB）回并，避免碎片请求

### 本项目最终分组（vite.config.ts）

```
react-core  priority 10  react/react-dom/scheduler
supabase    priority 9   @supabase/*
antd        priority 8   antd/@ant-design/@rc-component/rc-*  + entriesAware:true
motion      priority 8   motion/motion-dom/framer-motion
markdown    priority 7   react-markdown/micromark/mdast-*/unified…（仅论坛用，独立缓存）
vendor      priority 1   其余 node_modules
```

## 三、v4.0 实测结果

| 指标 | v3.6 | v4.0 |
|---|---|---|
| 最大 chunk | 801KB（乱序） | 386KB `antd~…core`（语义清晰） |
| 入口应用代码 | 448KB（混入 vendor） | 65KB（纯应用代码） |
| antd 分布 | 3 块撕裂 | 核心共享块 + 按页面裂解子块 |
| 重型页面组件（Table/Tree/DatePicker） | 全站买单 | 仅引用页面加载 |
| 缓存稳定性 | 共享模块一变全灭 | vendor 独立哈希，业务改动不影响 vendor 缓存 |

## 四、方法论沉淀

1. **chunk 审计脚本**：`build --sourcemap` 后读 `dist/assets/*.js.map` 的 `sourcesContent` 按字节聚合，比任何猜测都准（本文第一节的表格即产出）。
2. **API 以本机类型定义为准**：rolldown/vite 迭代快，博客过期严重；`node_modules/rolldown/dist/**/*.d.mts` 是当前安装版本的最终权威。
3. **分包调参循环**：改 groups → build → 审计 chunk 命名与大小 → 再调。`entriesAware` 是否开启差异巨大，务必实测。
4. GitHub Pages 是 HTTP/2，多 chunk 并行加载无代价；碎片化风险在请求数而非延迟。
