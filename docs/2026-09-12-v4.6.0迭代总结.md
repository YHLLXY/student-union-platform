# v4.6.0 迭代总结（Phase 4：权限收口 + 数据保险 + 无障碍）

> 2026-09-12。面向用户的交付明细、偏差与验证记录见
> `docs/plans/2026-09-06-全方位升级实施计划-v4.3至v4.6.md` 第十一节，本文件只写**经验**——
> 也就是「下一个接手的人如果不知道这些，会踩什么坑」。

## 一句话

这一版没有新功能：把「任何登录用户都能给自己提权、能删光任务公告」这个洞堵上，
给数据加了每周自动备份，给网站加了外部拨测，并出了第一份无障碍审计报告。
**最值得留意的不是代码，而是验证方式变了**——见经验 1。

## 经验

### 1. 「有测试护栏」≠「什么都能测」：先问「谁来验证它」

计划里写的是「细粒度 RLS 在 E2E 就绪后执行，回归有保障」。真动手才发现这个前提不成立：
**E2E 与单测打的是 dev-stub，而 stub 不实现 RLS**——它保证的是报文形态（`.or()`、`cs.{}`、
`count=exact`、列默认值），不是权限语义。策略写错（该放行的拒了、该拒的放行了），
`npm test` 与 `npm run test:e2e` 会**全绿**。

于是有了 `supabase-verify-v4.6.0.sql`：在事务里 `SET ROLE authenticated` + 注入
`request.jwt.claims` 的 sub，冒充 volunteer / dept_head / president 去撞真实策略，
逐条断言「该放行的放行、该拒绝的拒绝」，末尾 `ROLLBACK` 不留痕。

**可迁移的判据**：每次引入「不在应用层的语义」（RLS、触发器、RPC 授权、备份脚本），
先回答一个问题——**谁负责验证它？** 如果答案是「E2E」，那就要检查 E2E 是不是真的跑在那层语义上。
答不上来的时候，就得写一份能被机器执行的自证脚本。

### 2. 匿名角色的能力，比你想的大

实测（拿 anon key 直打生产 REST，只调纯函数、不写数据）：

| 函数 | 改前 | 说明 |
|------|------|------|
| `role_level('volunteer')` | **200 / 0** | anon 可调，直接返回数据 |
| `is_organizer()` | **200 / false** | anon 可调 |
| `semester_of()` | **200 / "2026-2027-1"** | anon 可调 |
| `check_in_ticket('PROBE')` | **200 {forbidden}** | anon 可调（内部守卫挡住了，但权限本身不该给） |
| `ticket_qr_token(<随机 uuid>)` | **400 {票券记录不存在}** | 同上 |
| `verify_ticket_qr_token('PROBE')` | 401 / 42501 | Phase 2 已显式收口 ✓ |

根因：Supabase 建库时对 public schema 执行了
`ALTER DEFAULT PRIVILEGES … GRANT ALL ON FUNCTIONS TO anon`，**之后新建的函数默认 anon 也能调**。

**两条结论**：① 新函数一律「先 `REVOKE … FROM PUBLIC, anon` 再 `GRANT`」，别指望默认值；
② **「函数内部有守卫」不等于「应该给它权限」**——最小权限是独立的一件事，不要互相替代。
（顺带：`REVOKE … FROM PUBLIC` 会连带收回 `authenticated`，因为 PUBLIC 是所有角色的集合，
所以顺序必须是「先 REVOKE 再 GRANT」，写反了会让策略里用到的判定函数报 42501。）

### 3. 「只允许写自己」的策略，可能正在放行自我提权

最初给 `users` 写的 INSERT 策略是 `WITH CHECK (auth_id = auth.uid())`——看起来只是「允许注册写自己那行」。
但 `role` 是**请求体带来的**：任何人拿到一张邀请码注册后，都能直接
`POST /rest/v1/users {"auth_id": 自己, "role": "president", ...}`。策略拦的是「写谁」，
拦不住「写成什么角色」。

最终落法：`users` **不要 INSERT 策略**（RLS 默认拒绝＝没有入口），注册走 `register_user()`
（SECURITY DEFINER），由它复核邀请码并**从邀请码推导 role 与 department**。

**可迁移的判据**：写策略时把请求体里会被写入的字段过一遍，逐个问
「这个值能不能决定权限？」能决定（`role`、`department`、`status`、`checked_in_at`、计数器列），
就必须由数据库算出来或由触发器守住，不能由客户端提交。

### 4. 策略与触发器是互补的两道门，谁也替不了谁

- 策略回答「**谁可以碰这一行**」，但看不到「这次更新动了哪些列」——同一个策略
  无法区分「改自己的昵称」和「把自己 role 改成 president」；
- 触发器回答「**这次写入了什么**」，但没有行级身份概念。

所以 `users` 的防线是两件东西：UPDATE 策略（本人或管理员才能碰这行）+ `BEFORE UPDATE OF
role, department, student_id, auth_id` 守卫触发器（只有管理员能改前两者，后两者一律不可变）。
项目里已有三处同样的组合（审核权、签到权、置顶权），本次是第四处。

### 5. 「收敛权限」要**先建新策略、后拆旧的宽松策略**

建表/加列可以随便排顺序，改权限不行：permissive 策略之间是**并集**，两套并存时权限仍是旧的宽松状态；
但反过来先拆后建，中间会出现「一条策略都没有」的真空期，线上正在操作的请求会被直接拒掉。
第二十部分的顺序因此固定为「① 建全部新策略 → ② 最后统一摘掉 `authenticated_full_access`」，
并在文件头写明原因，免得下一个人「顺手」把顺序调回去。

### 6. E2E 里等页面就绪，不能用 UI 文案

写 a11y 扫描用例时踩的：点侧边栏切模块后 URL 立刻变，但**模块是懒加载的**，新页面的 JS 还在下载，
这段时间 DOM 里仍是上一页——axe 扫到的是上一页，问题被记到了错误的页面名下
（首跑把任务管理缺 label 记成了部门公告）。

第二个坑紧接着来：改用「等待该页的『发布任务』按钮出现」后仍然不灵——因为**工作台的快捷入口里也有
「发布任务」**，在上一页就命中了。最终改成：每个页面 `page.goto('/#/xxx')` 整页加载（从根上消除陈旧 DOM）
+ 用该页**独有**的标题/副标题做锚点。

**可迁移判据**：E2E 里「等某页就绪」的锚点必须是该页独有的，且不能是跨页面复用的通用文案/通用按钮。

### 7. 导出/同步类脚本的头号敌人是「静默截断」

PostgREST 单次最多返回 1000 行。一个不分页的备份脚本会**成功地**只备下前 1000 行，
manifest 写着成功、恢复也「成功」——直到真正需要恢复的那一天才发现少了数据。
所以备份脚本里写了两道：`Range` 头翻页 + 用 `Prefer: count=exact` 的总数**核对实抓行数**，
对不上直接非 0 退出。实测灌 2500 行验证分页确实取满。

同类判据：任何「把远端数据搬到本地」的脚本，都要有一个「总量核对」和一个「损坏检测」
（本脚本对每个文件记 sha256，恢复前先校验，篡改一个字节即拒绝写入）。

### 8. 改权限的 SQL，验收脚本要「可执行 + 无副作用 + 可回滚」

`SET ROLE` 的约束是「禁止在 SECURITY DEFINER 上下文里用」，DO 块是 invoker，所以可用——
但为了让这份脚本在任何环境都不白费，做了三处防御：

- **预检降级**：先试一次 `SET ROLE`/`RESET ROLE`，不行就把第二段整体标记为 `[跳过]` 并给出替代方案，
  而不是让整个脚本报错（否则用户拿到的只有一条看不懂的错误）；
- **探测不写真实数据**：允许类更新一律用 `SET 列 = 列` 的无变化写法；退票探测针对**自造标记票券**；
  唯一真实改值的两条（管理员改角色）在探测内立刻用补偿语句改回；
- **自证无残留**：结尾核对「标记数据 0 残留」与「被冒充的志愿者仍是志愿者」。

### 9. 把不变量从调用点搬进数据库，往往一次解决一类问题

注册原本是「前端查邀请码 → 直插 users（role 由前端传）→ 前端回写 used_count」。
搬进 `register_user()` 之后，一次解决三件事：角色不能自选、核销与建号在同一事务（消除 TOCTOU 竞态，
与 P0-01 抢票同一类问题）、表侧不再需要 INSERT 策略。

代价是**行为变更**：并发或码失效时，注册从「码废了但人建出来了」变成明确拒绝。
这类「顺手修好但会改变表现」的改动，必须写进文档与交付说明，不能埋在 commit 里。

### 10. 每一种验证手段都有适用范围，用错会得到**假警报**

三条实测踩到的边界，都是「方法本身没错，用错了地方」：

- **「对比线上与本地 dist 的 chunk 哈希」不能证明部署是否最新**。收尾复测时线上入口 chunk 与本地
  差 30 处，一度以为部署没生效；逐处核对后发现**全部是指向其他 chunk 的 8 位哈希名**，
  而 13 个入口静态引用的 chunk 名字完全相同——同一份源码在 CI（Linux）与本地（Windows）
  构建出的**懒加载 chunk 命名并不逐字一致**。判定「线上是不是这次构建」要用
  `version.json` / `sw.js` 的版本号 + CI 那次运行的状态，chunk 名对比只当参考。
  （已在 CLAUDE.md 的线上排查章节写明，并开 ISSUES #16 建议加 `build-info.json` 一劳永逸。）
- **`axe` 查不出焦点顺序**：它只做静态规则。要验证「键盘能不能走完表单、顺序对不对」，
  只能真的按 Tab 走一遍。
- **`npm test` 查不出 RLS**（见经验 1）。

**可迁移判据**：断言之前先问「我信的是哪个观察量？这个观察量覆盖不覆盖我要证明的东西？」
观察量选错时，测试仍然会绿——只是绿得没有意义。

### 11. 权限断言要按**操作类型**选观察量

写自证脚本时先按「一律期望抛异常」写了 28 条，其中一条（负责人改成员角色）直接写错：
**RLS 对不同操作的拒绝表现不一样**——

| 操作 | 被策略拒绝时的表现 |
|------|-------------------|
| `SELECT` | 返回 0 行（不报错） |
| `DELETE` / `UPDATE`（USING 不匹配） | 影响 0 行（不报错） |
| `INSERT` / `UPDATE`（WITH CHECK 不通过） | **抛 42501** |
| 触发器 `RAISE EXCEPTION` | 抛 P0001 |

所以「期望值」必须区分「0 行」和「抛异常」；把 UPDATE 的拒绝写成「期望异常」会得到假失败，
反过来把 INSERT 的拒绝写成「期望 0 行」会得到假通过。

### 12. 审计/报告类用例：先落产物，再断言

a11y 那条用例第一版是「边扫边断言」，于是门禁失败时**什么都没留下**——
只拿到一条错误，看不到完整清单，还得再跑一遍。改成「扫完所有页面 → 写报告 → 最后统一断言」之后，
一次运行就能拿到全部 critical 及其定位。

**判据**：产出物是交付物的一部分时，它的生成不能依赖断言通过。

### 13. 新的断言优先复用既有 helper，别重新踩已知的坑

项目里 `tests/e2e/helpers.ts` 的 `btn()` 早就封了「antd 恰好两个汉字的按钮会被插空格」（`继续` → `继 续`）。
我新写焦点顺序用例时直接用文本比对，又踩了一遍（`继续` 匹配不上），浪费一轮。

**判据**：写新用例前先扫一眼 helpers 里已有什么——那里沉淀的每一条都是踩过的坑。

### 14. 「待用户执行」是一次**无证据交接**，必须配机器可查的就位证据

**这是本轮代价最大的一次失误，而且它不是技术错误。** 第十九部分（Phase 3 数据层）交付时写的是
「待你在 Supabase 执行」，之后没有任何环节能回答「它到底执行了没有」。前端照常发版，于是线上：
论坛页报「帖子加载失败」（列表按不存在的 `pinned_at` 排序 → `42703`）、个人资料保存失败
（更新体固定带不存在的 `contact_phone`）、新人引导落库失败。**几天里没人发现，因为功能代码本身是「对」的**。

暴露它的也不是流程，而是巧合：Phase 4 的验收表里恰好有两行 `forum_likes / forum_bookmarks` 策略数，
打出 `[缺失] 只有 0 条`——**而这句话还把人引向了错误方向**（看着像「策略被人删了」，实际是「表根本不存在」）。

三条可迁移的做法：

1. **交付物凡是「要靠人在别处手动做一次」的，就给它配一个机器可查的判据**。本轮的落地是
   `npm run probe:db`（`scripts/probe-schema.mjs`）：只用 anon key 做只读探测（`limit=0`，不取任何行），
   按批次回答「表/列在不在」，退出码非 0 即未就位。它把「用户说执行了」变成「库自己说执行了」。
2. **判据要能区分两种原因**。`[缺失] 只有 0 条` 把「表不存在」和「策略被删」混为一谈；
   现在验收表分成两句，各自给出下一步该做什么。
3. **顺带发现的探测技巧**：PostgREST **先解析、后鉴权**，所以即使用了「读不到任何表」的 anon key，
   也能靠 `42703`（列不存在）判断某个列在不在；表则在 `404 / PGRST205`（不存在）与
   `401 / 42501`（存在但无权限）之间区分。这个技巧让「无 DB 权限的 AI / 无 service_role 的本地环境」
   也能核对 schema——**但必须配一个对照探测**（探一张确定不存在的表），否则 key 写错时所有 401 都会被误读成「已就位」。

同类判据：**任何「交付了但需要外部动作才生效」的东西，都要有一个能自动回答「生效了吗」的检查**，
否则它会在「看起来完成了」的状态里躺着，直到用户撞上功能故障。

### 15. 验收脚本本身也会「假通过」：异常被当成拒绝

同一轮里的连带发现：自证脚本用「探测语句抛异常」代表「策略拒绝了」——这在表不存在时也成立
（`42P01 undefined_table` 同样抛异常）。第十九部分没执行的情况下，所有 `forum_likes` 的 deny 断言
会**以「环境缺失」伪装成 `[OK]`**。

修法：把 `42P01 / 42703` 从「被拒绝」里排除，单独报「环境缺失」；并在前置对象缺失时让整段 `[跳过]`
而不是逐条给出结论。

**判据**：写「期望失败」的断言时，要问一句「还有哪些原因会失败？它们算通过吗？」——
只有「因正确的原因失败」才算通过。

**实跑后又补了三条「报告自己说不清」的**（首次真跑自证脚本暴露的，都属同一类）：

- 报「1 条对 PUBLIC 生效」却**不说是哪一条** → 只能回来翻脚本对名字，查出是 `platform_guides`
  的读策略漏写 `TO authenticated`（不写 `TO` 就是 `TO PUBLIC`，含 anon）。现在把那一条的名字直接打出来，
  并在第二十部分一并收口。**报数必须报名**——否则用户拿到的是一道谜题。
- 第二段整段跳过的原因是「库里没有可冒充的 volunteer」，而原提示把两种可能并列
  （缺 volunteer／缺部门非空的 dept_head），**等于没说**。现在分开报各有多少名。
- 「结果」列把 `[跳过]` 显示成 `[失败]`，读起来像策略有问题。跳过一次不是失败，
  现在单列 `[跳过]` 一档，并说明「第一段结果仍然有效」。

**判据**：验收报告的每一行都要能让人**直接行动**——说清哪个对象、缺什么、下一步做什么；
「有 1 条不合规」这种句子对执行者毫无用处。

### 16. 交付给用户的脚本会被重跑，幂等不是加分项

用户补跑 Phase 3 之后又跑了一遍第二十部分，撞上：

```
ERROR: 42710: policy "notifications_select_own" for table "notifications" already exists
```

根因很小：改策略名时只 `DROP` 了旧名字（`"Users can read own notifications"`），没删新名字，
而 `CREATE POLICY` **没有 `IF NOT EXISTS`**。第二十部分里这样漏了 6 条（`notifications` 与
`platform_guides` 各 3 条），第一条就把整份脚本顶住了——SQL Editor 把整段当一个事务，
用户看到的只有「already exists」，既看不出「这个脚本不能重跑」，也看不出后面还有 5 条同样的坑。

三点可迁移的：

1. **「我写的脚本」和「用户会怎么用它」是两件事**：我按「一次干净执行」写、按「一次干净执行」测，
   但用户会在补数据层、复查、复现问题时反复重跑。凡是交给别人的一次性脚本，默认它会被跑第二遍。
2. **靠人记住不行，要让工具每次都说**：与「DDL 顺序检查」同源（那次是 42703），这次给
   `scripts/check-sql.mjs` 加了第四关**可重跑检查**——`CREATE POLICY` / `CREATE TRIGGER` 之前
   必须有同名 `DROP … IF EXISTS`。九个交付文件现在四关全过，以后再漏一次会在交付前被拦下。
3. **写检查本身也会假报警**：第一版直接在原文上正则，把第四部分里**整段注释掉**的
   `-- CREATE POLICY "users_select_own" …` 也算成违规，报出 23 项假异常。检查必须只看代码区
   （切分器早就有 `code` 字段，直接用它）。

**判据**：给用户的 SQL，交付前不仅要问「第一次执行对不对」，还要问「第二次执行会怎样」。

## 给下一次接手的注意事项

1. **动数据库权限前，先读 `supabase-migration.sql` 第二十部分的文件头**——六条不变量（读侧留宽的 5 张表、
   辅助函数为什么必须 SECURITY DEFINER 且只给 authenticated、`users` 为什么没有 INSERT 策略、
   守卫触发器管什么、anon 的默认授权坑、先建后拆的顺序）都写在那里。
2. **改完权限一定要跑自证脚本**，别用 `npm test` 绿了当证据（见经验 1）。
3. **发版后先跑 `npm run probe:db`**（3 秒、只读）——先确认「表/列都在」，再谈策略对不对（见经验 14）。
4. **新增函数/表后**，检查 `anon` 是否又被默认授权（`REVOKE` 已取消默认授权，但显式 `GRANT` 过的要复查）。
5. **备份与恢复的手工操作**见 `docs/backup-restore.md`；恢复脚本必须 `--yes`，不带只校验。
6. **E2E 用的是固定端口**（stub 9913 / 站点 4173），**同一时刻只能有一个 runner**：
   在后台跑全量的同时再单独跑某个 spec，会互相抢端口，报错长这样——`TypeError: fetch failed`。
   要单跑就等上一次结束。
7. **断言之前先想清楚观察量**（见经验 10/11/15）：RLS 的拒绝是「0 行」还是「抛异常」按操作分，
   且「抛异常」要排除环境缺失；部署是否最新看版本号与 CI 状态，别看 chunk 哈希。
